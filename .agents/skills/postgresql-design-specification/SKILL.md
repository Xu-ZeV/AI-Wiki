# PostgreSQL 数据库设计规范（PostgreSQL 14+）

本规范把上游 `Highflyer/MySQL-Design-Specification`（commit `14f78853e8b601b78ce2abfc0120b4cf55e06e37`）的 109 条编号条款逐条落地到 PostgreSQL 14+。每条规范条目都带上游条款号标注，形如 `[2.1.3-5]`；纯 PG 补充条目标注 `[新增]`。上游确有不可移植之处的条款，仍显式写出并说明理由，不做静默删除。

## 支持文件

- `references/upstream-mysql-design-spec.md`：上游原文全文，本 skill 的唯一内容来源（109 条条款 + 2 处【异议】）。
- `references/mysql-to-postgresql-mapping.md`：109 行逐条对照映射表 + 4 行条款冲突裁决。

## 适用范围

- 面向线上 OLTP 业务的 PostgreSQL 14+ 库、schema、表、字段、索引、分区、字符集设计与 SQL 编写评审。
- 适用于表结构评审、DDL 上线前检查、慢 SQL 治理、事务边界评审。

## 不适用范围

- 不替代官方文档与具体版本发布说明；版本敏感特性一律以目标实例 `SELECT version();` 为准。
- 不覆盖 PG 运维（备份恢复、复制拓扑搭建、连接池参数调优手册、监控告警阈值）。
- 不覆盖分库分表中间件、FDW 与逻辑复制的完整选型。

## 规范分级

沿用上游三级，遵守优先级从高到低：

- 【高危】：违反会直接造成线上数据错乱或不可用，评审直接打回。
- 【强制】：违反必须整改，DBA/评审人有权打回。
- 【建议】：推荐做法，偏离时需在评审记录中写明理由。

上游分级与本 skill 分级一一对应，不新增级别；上游 2 条【异议】按「条款冲突裁决」处理。

## 2.1 数据库对象设计

### 2.1.1 一般命名规则

- [2.1.1-1] 标识符一律使用小写。PG 中未加引号的标识符会被折叠为小写，混写只会带来隐藏错误。
- [2.1.1-2] 名称不含空格，用下划线连接单词。
- [2.1.1-3] 名称只用英文字母，不含数字。
- [2.1.1-4] 名称有效、可理解。
- [2.1.1-5] 名称自解释，读名知义。
- [2.1.1-6] 名称不超过 32 个字符。补充 [新增]：PostgreSQL 标识符硬上限是 63 字节，超出会被静默截断，因此 32 字符的约定在 PG 中依旧成立且更安全。
- [2.1.1-7] 避免使用前缀。

### 2.1.2 库与 schema

- [2.1.2-1] 遵守 2.1.1 全部一般命名规则。
- [2.1.2-2] 使用单数。
- [2.1.2-4] 名称格式为 `<业务系统名>_<子系统名>`。PG 中「库」对应 database 与 schema 两级：跨子系统共用一个 database 时，用 schema 承载子系统名；确需物理隔离时才拆 database。
- [2.1.2-5] 分片命名沿用同一口径：`<库通配名>_<编号>`（编号从 0 起递增）或 `<库通配名>_<时间>`。
- [2.1.2-6] 创建 database 时必须显式指定编码与排序规则（collation），例如 `CREATE DATABASE db_name ENCODING 'UTF8' LC_COLLATE 'zh_CN.UTF-8' LC_CTYPE 'zh_CN.UTF-8';`，多语言场景优先 ICU collation。补充 [新增]：PG 的 UTF8 不存在上游 MySQL 所述 3 字节限制，因此上游的 utf8/utf8mb4 双选在 PG 中统一为 UTF8；database 的 encoding/locale 创建后基本不可就地变更，必须建库时定好。

### 2.1.3 表

- [2.1.3-1] 遵守 2.1.1 全部一般命名规则。
- [2.1.3-2] 使用单数。
- [2.1.3-3] 相关模块的表名之间体现连接关系，例如 `user` 与 `user_login`。
- [2.1.3-4] 上游要求建表显式指定字符集；PG 中编码与排序规则自 database 继承，一般不需要逐表声明，仅在需要特殊排序时写列级 `COLLATE`。因此本条落地为「编码由库级统一，特殊排序需求用列级 collation 显式声明」。
- [2.1.3-5] 上游要求显式指定存储引擎并一律用 InnoDB。PG 只有堆表 + MVCC + TOAST 一种行存储模型，没有存储引擎选项，等价落地为：默认使用普通堆表；需要物理层分离时用表空间（tablespace）或声明式分区；大对象自动 TOAST 行外存储。
- [2.1.3-6] 建表必须写注释，使用 `COMMENT ON TABLE ... IS '...';` 与 `COMMENT ON COLUMN ... IS '...';`（可被 `psql \d+` 与客户端读取）。
- [2.1.3-7] 主键约定：(1) 主键命名为 `id`，类型为 `bigint`，使用 `GENERATED BY DEFAULT AS IDENTITY`（PostgreSQL 10 起可用），不要再用历史遗留的 `serial`；(2) 业务标识列（如 `user_id`、`order_id`）不设为主键，另建 UNIQUE 约束/唯一索引。上游该条的理由是 MySQL 聚集索引随机插入引发 page 分裂；PG 主键是独立 btree 索引、表数据按 ctid 存放，代价模型不同，但业务键单独建唯一索引的做法同样推荐。
- [2.1.3-8] 核心表（用户表、资金相关表）必须有创建时间 `create_time` 与最后更新时间 `update_time`，类型用 `timestamptz`，默认值 `now()`（由 [2.1.5-8] 的类型取舍决定）；更新时由应用显式赋值，或对低写入表使用触发器（需评审）。
- [2.1.3-9] 表中字段尽量全部 `NOT NULL`，并按业务定义 `DEFAULT`。PG 中 NULL 仅在行尾不占用额外字节，但 NULL 带来的聚合偏差、迁移歧义、三值逻辑风险与上游一致，故保留本条要求。
- [2.1.3-10] 大字段（文本、二进制大对象）建议垂直拆分到独立表，只在需要读取时才查询。PG 中 TOAST 会自动把超阈值的大值移出行外，但随行读取仍会带来 I/O 与网络开销。
- [2.1.3-11] 适度反范式：把频繁连接的字段冗余到其它表（如 `username` 冗余到 `user_login_log`），以减少连接查询。
- [2.1.3-12] 中间表用于保存中间结果集，名称必须以 `tmp_` 开头；备份表用于快照，名称必须以 `bak_` 开头；中间表与备份表定期清理。PG 补充 [新增]：会话级中间结果优先用 TEMPORARY 表或 `UNLOGGED` 表，只读快照可用物化视图。
- [2.1.3-13] 超过 100 万行的大表执行 `alter table` 必须经过审核，并在业务低峰期执行。PG 补充 [新增]：优先使用不重写的变更——加列带**非易失（non-volatile）**默认值（PostgreSQL 11 起才不重写表；易失默认值如 `clock_timestamp()`、存储生成列、identity 列、带约束的 domain 类型仍会重写表与索引）、`CREATE INDEX CONCURRENTLY`、先 `NOT VALID` 加约束再 `VALIDATE CONSTRAINT`（`NOT VALID` 自 9.1 起用于外键、9.2 起扩展到 CHECK），把一次大变更拆成多次小变更。非易失默认值判据见官方 ALTER TABLE：https://www.postgresql.org/docs/current/sql-altertable.html 。

### 2.1.4 字段名

- [2.1.4-1] 遵守 2.1.1 全部一般命名规则。
- [2.1.4-2] 尽可能短，一到两个单词。
- [2.1.4-3] 避免使用保留字作字段名（如 `order`、`date`、`name`），可加前缀区分，如 `user_name`、`signup_date`。PG 保留字集合与上游不同，可用 `pg_get_keywords()` 自查。
- [2.1.4-4] 避免字段名与表名相同，以免编写查询时混淆。
- [2.1.4-5] 在数据库模式上定义外键。见「条款冲突裁决」第 3 条：PG 默认启用声明式外键。
- [2.1.4-6] 避免使用缩写或首字母缩写词。
- [2.1.4-7] 外键列必须带表名语义，形如 `blog_id` 表示引用博客表主键。

### 2.1.5 字段数据类型优化

- [2.1.5-1] 自增列推荐 `bigint`，避免 32 位溢出。PG 落地：`bigint GENERATED BY DEFAULT AS IDENTITY`；identity 底层仍是序列，但没有上游 `auto_increment` 的表级自增锁竞争。
- [2.1.5-2] 选择性很低的状态、类型字段（`status`、`type`）用 `smallint` 或 `int` 节省空间。
- [2.1.5-3] IP 字段：PG 原生提供 `inet` 类型，直接比较与索引，且支持 `<<` 等网段运算；不再需要上游的 int + `inet_aton`/`inet_ntoa` 或应用层 `ip2long` 转换（这些函数与做法是 MySQL 语境）。
- [2.1.5-4] 上游不推荐 `enum`/`set`，其异议建议改用枚举 + 严格模式。PG 见「条款冲突裁决」第 1 条：优先 `text` + `CHECK`，或原生 `enum`（支持 `ALTER TYPE ... ADD VALUE`，但删改值困难）。
- [2.1.5-5] 上游不推荐 `blob`、`text` 大类型。PG 中 `text` 与 `varchar(n)` 性能无差异，超阈值自动 TOAST 行外存储；上游所述 overflow-page 与 compact 行格式属于 MySQL 概念，本条落地为「大值用 `text`/`bytea`，读多写少的列垂直拆表」。
- [2.1.5-6] 金额字段：PG 用 `numeric(p,s)` 存储精确十进制，不存在上游所述 decimal 二进制编码的精度与效率问题；仅在应用层明确要求分单位整数时，才用 `bigint` 存「分」。
- [2.1.5-7] 文本用变长类型。上游给出的 65535 字节行上限、utf8 下的字符数与 mediumtext/longtext 分级都是 MySQL 语境；PG 统一建议 `text`（不加长度即为无约束变长），需要长度约束时用 `CHECK (length(col) <= n)` 表达业务语义。
- [2.1.5-8] 时间类型：PG 统一用 `timestamptz`（`timestamp with time zone`）；确有明确理由才用 `timestamp`（无时区），并在注释中写明。不用整数存时间戳；需要 epoch 运算时用 `extract(epoch from ...)` 与 `to_timestamp()`，替代上游的 `unix_timestamp()`/`from_unixtime()`。

### 2.1.6 索引设计

- [2.1.6-1] 每张表必须有主键 `id`（`bigint` + `GENERATED BY DEFAULT AS IDENTITY`），且主键值禁止更新。
- [2.1.6-2] 主键名以 `pk_` 开头、唯一键以 `uk_` 开头、普通索引以 `idx_` 开头，全小写，后缀取表名/字段名或缩写。
- [2.1.6-3] 上游要求索引类型一律 btree。PG 中 btree 是默认索引类型，并可用 `INCLUDE` 覆盖索引（PostgreSQL 11 起）；此外还按场景使用 gin（`jsonb`、数组、全文）、gist（几何/范围）、brin（大表按物理顺序的范围扫描）、hash（仅等值比较，不支持范围）。选型必须写明理由。
- [2.1.6-4] 单个索引记录不可过大。PG 的 btree 索引项不得超过页的约 1/3（官方口径 cannot exceed approximately one-third of a page，见 https://www.postgresql.org/docs/current/btree.html ），超长值应改为表达式索引或 `substr(col,1,n)` 前缀索引；hash 索引只支持等值比较、丢范围能力，不能用来解决单纯的长度问题。
- [2.1.6-5] 单表索引个数建议不超过 5 个（写入放大是主要成本，PG 每个索引都要维护 WAL 与 VACUUM）。
- [2.1.6-6] 优先建联合索引，并把区分度最高的字段放在最前面（区分度可用 `count(distinct col)` 估算）。
- [2.1.6-7] 多表连接时保证被驱动表的连接列上有索引。
- [2.1.6-8] 避免冗余索引：已有 `key(a, b)` 时 `key(a)` 为冗余索引；PG 中额外注意重复前缀的 btree 索引与前缀完全相同的表达式索引。
- [2.1.6-9] 选择性超过 20% 时全表扫描可能优于索引。PG 落地：先用 `EXPLAIN (ANALYZE, BUFFERS)` 实测；大表范围扫描可改用 brin 或 partial index（部分索引，带 `WHERE` 谓词），并用 `ANALYZE` 保持统计信息准确。

### 2.1.7 分库分表、分区表

- [2.1.7-1] 分区键必须有索引，或位于组合索引首列。
- [2.1.7-2] 单个分区表的分区（含子分区）个数不能超过 1024。PG 说明 [新增]：沿用上游 1024 作为运维上限口径；分区越多，规划器枚举分区、加锁与运行期开销越大，经验上控制在数百个以内并实测。此外受官方分区 Limitations 约束——唯一约束/主键必须包含全部分区键，见 https://www.postgresql.org/docs/current/ddl-partitioning.html 。
- [2.1.7-3] 上线前必须由研发或 DBA 明确分区表的创建策略与清理策略（PG 常用 `DETACH PARTITION` + 归档表，避免 `DELETE` 大范围数据）。
- [2.1.7-4] 访问分区表的 SQL 必须包含分区键，以触发 PG 的分区裁剪。
- [2.1.7-5] 单分区大小与总量需设上限（建议单分区不超过 2GB、总量不超过 50GB、分区数不超过 20 个）；PG 用 `pg_relation_size()`、`pg_total_relation_size()` 度量。
- [2.1.7-6] 对分区表执行 `alter table` 必须在业务低峰期。
- [2.1.7-7] 采用分库策略时，库的数量不超过 1024。
- [2.1.7-8] 采用分表策略时，表的数量不超过 4096。
- [2.1.7-9] 建议单分表不超过 500 万行。上游用 ibd 文件大小衡量，PG 改用 `pg_total_relation_size()` 观察表与索引总大小。
- [2.1.7-10] 水平分表尽量用取模，日志与报表类数据按日期分表；PG 中优先用声明式分区（RANGE 按时间、HASH 取模），以列表分区处理枚举维度。

### 2.1.8 字符集与排序规则

- [2.1.8-1] database、schema 内表与列编码必须一致，统一为 UTF8；列级 collation 也应保持一致，混用 collation 会导致索引失效与排序结果不一致。
- [2.1.8-2] 应用端字符集必须与数据库一致：客户端连接显式设置 `client_encoding = 'UTF8'`，避免隐式转换。

### 2.1.9 程序层 DAO 设计建议

- [2.1.9-1] 新代码不要用重 ORM 模型，推荐手写 SQL + 绑定变量；PG 中绑定变量即扩展查询协议参数（`$1`），可避免 SQL 注入并复用执行计划。
- [2.1.9-2] 应用连接 PG（或 Redis）必须具备连接超时与失败重连机制，重试必须有间隔（PG 侧配合 `idle_in_transaction_session_timeout` 防止挂起事务占用连接）。
- [2.1.9-3] 应用报错尽量透出数据库原生错误信息，便于排查。
- [2.1.9-4] 使用连接池时必须按业务配置初始/最小/最大连接数与超时、回收机制；PG 每个连接是独立进程，默认 `max_connections` 有限，超配会直接耗尽数据库连接。
- [2.1.9-5] 日志/历史类表必须在上线前制定清理或归档方案（PG 中可用分区 + `DETACH` 归档，避免大范围 `DELETE` 造成表膨胀）。
- [2.1.9-6] 应用设计阶段必须考虑复制延迟：强一致读走主库（或对只读会话设置 `default_transaction_read_only` 前的路由判断），容忍延迟的读才路由到备库。
- [2.1.9-7] 并发更新同一批数据时优先基于主键更新，减少行锁持有范围。
- [2.1.9-8] 业务逻辑之间的加锁顺序保持一致，避免死锁。
- [2.1.9-9] 单表读写比大于 10:1 的热点行或热点列可放入缓存，降低数据库压力。

## 2.2 SQL 编写

### 2.2.1 DML 语句

- [2.2.1-1] `select` 必须写出具体字段名，禁止 `select *`。
- [2.2.1-2] `insert` 必须写出具体字段名，禁止 `insert into t values(...)` 这种省略列名的写法。
- [2.2.1-3] 批量 `insert ... values(...),(...)` 的值个数不要超过 5000 个。补充 [新增]：PG 中更大的批量导入优先用 `COPY` 或 `unnest` 展开，减少 WAL 与网络往返开销。
- [2.2.1-4] `select` 尽量不用 `union` 而用 `union all`，`union` 子句个数限制在 5 个以内（去重有额外排序与哈希开销）。
- [2.2.1-5] `in` 值列表限制在 500 以内。
- [2.2.1-6] 事务内批量更新要控制数量并做必要的 sleep，少量多次。
- [2.2.1-7] 上游要求事务涉及的表必须是同一存储引擎。PG 落地：PG 没有存储引擎概念、也不支持跨 database 事务，因此本条等价为「一个事务只允许访问同一 database 内的对象」，跨库写入须用 FDW/两阶段提交并显式评审。
- [2.2.1-8] 写入与事务发往主库，只读 SQL 发往从库。PG 落地：主库写、hot standby 读；注意备库查询与 `synchronous_commit` 的关系，热点只读可走备库但对一致性敏感的业务必须回主库。
- [2.2.1-9] 除 100 行以内的静态小表外，DML 必须有 `where` 条件且走索引查找。
- [2.2.1-10] 生产环境禁止使用 hint。PG 查询计划器不接受 MySQL 式 hint，且上游列举的 `sql_no_cache`、`force index`、`ignore key`、`straight join` 在 PG 中均不存在；确需干预计划时使用 `pg_hint_plan` 扩展或改写 SQL，并把理由写进评审记录。
- [2.2.1-11] `where` 条件等号左右字段类型必须一致（PG 中类型不一致会导致隐式转换、可能无法命中索引）。
- [2.2.1-12] `select`/`update`/`delete` 必须有 `where` 子句，且条件使用索引查找。
- [2.2.1-13] 强烈不推荐大表全表扫描；100 行以内静态表例外。查询数据量不要超过表行数的 25%。
- [2.2.1-14] `where` 中禁止只使用全模糊 `like '%...%'`，必须有其它等值或范围条件。补充 [新增]：确实需要全文检索时用 gin 索引 + 全文检索或 `pg_trgm`。
- [2.2.1-15] 索引列不要套函数或表达式。PG 放宽说明 [新增]：PG 支持表达式索引，`CREATE INDEX ON t (lower(name))` 后 `where lower(name) = 'admin'` 可以走索引；但仍要求索引与查询表达式严格一致，否则不生效。
- [2.2.1-16] 减少 `or` 的使用，可把 `where a = 1 or b = 2` 改写为 `union` 并在各条件上分别建索引；PG 中也可依赖 BitmapOr，最终以 `EXPLAIN` 实测为准。
- [2.2.1-17] 深分页优化：`limit 10000, 20` 改为基于主键的 keyset 分页 `where id > 10000 limit 20`。

### 2.2.2 多表连接

- [2.2.2-1] 禁止跨 DB 的连接。PG 落地：同一 database 内的 schema 之间连接是正常用法；真正禁止的是跨 database 的 FDW/远程连接（会引入不可控的远程代价与耦合）。
- [2.2.2-2] 禁止在更新类 SQL 中使用连接，例如 `update t1 join t2 ...`。PG 落地：`UPDATE ... FROM` 语法合法，但仅在必须时使用，且必须小批量并先在只读环境验证执行计划。
- [2.2.2-3] 不建议使用子查询。见「条款冲突裁决」第 2 条：PG 中 `IN (SELECT ...)`、`EXISTS`、`NOT EXISTS` 均可正常使用（官方手册并未承诺特定的半连接/子查询提升优化，属经验性判断）；务必避免 `NOT IN (子查询)` 的 NULL 语义陷阱。
- [2.2.2-4] 线上环境多表连接不超过 3 个表。
- [2.2.2-5] 多表连接推荐使用别名，`select` 列表用别名引用字段，例如 `select a.id from app.orders a where ...`（PG 中为 `schema.表` 形式）。
- [2.2.2-6] 多表连接时尽量选择结果集较小的表作为驱动表。

### 2.2.3 事务

- [2.2.3-1] 事务中 `insert`/`update`/`delete` 的操作行数控制在 2000 以内，`where ... in (...)` 的参数个数控制在 500 以内。
- [2.2.3-2] 批量操作要控制事务间隔，必要的 sleep 建议 5-10 秒。
- [2.2.3-3] 对自增主键表的插入并发控制在 200 以内。PG 补充 [新增]：identity 序列取值不走表级锁，但高并发插入的真实瓶颈在 WAL 与索引维护，仍按本条限制应用侧并发。
- [2.2.3-4] 设计必须考虑隔离级别带来的脏读、不可重复读、幻读影响。上游建议 `repeatable-read`（属于 MySQL 语境的建议）；PG 落地：默认使用 `read committed`，需要快照一致性时用 `repeatable read`（快照隔离），需要串行化正确性时用 `serializable`（SSI）并**必须**实现事务重试逻辑（序列化失败返回 40001）。
- [2.2.3-5] 事务内 SQL 不超过 5 个（支付类业务除外），避免长事务。
- [2.2.3-6] 事务内更新尽量基于主键或唯一键。上游理由是防止间隙锁；PG 没有间隙锁，但非索引条件更新会全表扫描并长时间持有行锁、阻碍 VACUUM 回收，因此本条同样成立。
- [2.2.3-7] 把典型外部调用（Web Service、文件存储）移出事务，避免长事务。
- [2.2.3-8] 对一致性敏感的 `select` 必须开启事务读主库。

### 2.2.4 排序和分组

- [2.2.4-1] 减少 `order by`；`order by`/`group by`/`distinct` 消耗 CPU，能与业务协商则放到应用端排序。补充 [新增]：PG 中大数据量排序还会溢出到 `work_mem` 之外的临时文件，需关注 `EXPLAIN` 的 sort/hash 节点。
- [2.2.4-2] 让 `order by`/`group by`/`distinct` 直接利用索引取到有序数据，例如 `key(a, b)` 支持 `where a = 1 order by b`。
- [2.2.4-3] 含 `order by`/`group by`/`distinct` 的查询，`where` 过滤后的结果集应保持在 1000 行以内。

### 2.2.5 线上禁用使用的 SQL 语句

- [2.2.5-1] 【高危】禁用带 `limit` 的 `update`/`delete`。PG 落地：PG 语法上就不支持 `UPDATE/DELETE ... LIMIT`，等价写法是 CTE + `ctid` 或主键子查询分批更新，或 `FOR UPDATE SKIP LOCKED` 并发消费；注意 `ctid` 在 UPDATE 或 `VACUUM FULL` 后会变化、不能当作行标识（官方 System Columns：https://www.postgresql.org/docs/current/ddl-system-columns.html ），CTE + `ctid` 写法必须逐批重跑。
- [2.2.5-2] 【高危】禁止使用关联子查询。见「条款冲突裁决」第 2 条：PG 中 `IN (SELECT ...)`、`EXISTS`、`NOT EXISTS` 均可正常使用，仅需避免 `NOT IN (子查询)`（NULL 语义陷阱，官方说明见 https://www.postgresql.org/docs/current/functions-comparisons.html ），性能以 `EXPLAIN (ANALYZE, BUFFERS)` 实测为准。
- [2.2.5-3] 禁用 procedure、function、trigger、views、event、外键约束。见「条款冲突裁决」第 3 条：PG 中声明式外键默认启用；只读视图可安全使用；触发器与存储过程仅在有必要时使用并需评审。
- [2.2.5-4] 上游禁用 `insert ... on duplicate key update`（MySQL 语法）。PG 落地为 `INSERT ... ON CONFLICT DO UPDATE`（PostgreSQL 9.5 起）：在没有独立错误时，`DO UPDATE` 保证「INSERT 或 UPDATE」的原子结果；只有 SSI 序列化失败、死锁，或 arbiter 唯一索引正被 `CREATE INDEX CONCURRENTLY`/`REINDEX CONCURRENTLY` 重建等情形，才需要应用侧重试。见官方 INSERT 文档 https://www.postgresql.org/docs/current/sql-insert.html 。
- [2.2.5-5] 禁止联表更新语句，如 `update t1, t2 where t1.id = t2.id ...`。PG 落地：改写为 `UPDATE ... FROM` 或先查后改，且必须小批量、走索引。

## 条款冲突裁决

1. **enum/set（[2.1.5-4] 及其【异议】）**：上游建议用 `tinyint`，异议建议用 `enum` + 严格模式。PG 结论：优先 `text` + `CHECK (col IN (...))`，或使用原生 enum（PG 的 enum 支持 `ALTER TYPE ... ADD VALUE`，自 v12 起该语句可在事务块内执行，但同一事务内仍不能立即使用新值，且删除或重排枚举值非常困难，官方说明 https://www.postgresql.org/docs/current/sql-altertype.html ）；状态字段量级大、取值稳定时可用 `smallint` + 应用层字典，并用 `COMMENT ON COLUMN` 记录取值含义。三种方案都要写明变更成本。
2. **关联子查询（[2.2.5-2] 及其【异议】）**：上游把关联子查询列为【高危】禁用。PG 结论：`IN (SELECT ...)`、`EXISTS`、`NOT EXISTS` 均可正常使用；官方手册并未给出「半连接/反连接与子查询提升」的承诺，这属于经验性判断，最终以 `EXPLAIN (ANALYZE, BUFFERS)` 实测为准，不以形式判定。仍建议避免 `NOT IN (子查询)`（NULL 语义陷阱，官方说明 https://www.postgresql.org/docs/current/functions-comparisons.html ），改写为 `NOT EXISTS`。
3. **外键禁令 vs 定义外键（[2.1.4-5]、[2.1.4-7] vs [2.2.5-3]）**：上游内部自相矛盾——前两条要求「在数据库模式上定义外键」「外键列必须具有表名及其主键」，后者要求「禁用……外键约束」。PG 结论：**默认启用声明式外键**（官方 Foreign Keys：https://www.postgresql.org/docs/current/ddl-constraints.html ），因为 PG 的外键在被引用列有唯一索引、引用列有索引时写入路径成本可控，不存在上游所担心的隐式全表扫描风险；例外情形需显式写出理由——超高写入分区表、分片/水平拆分后跨库引用、大批量导入场景可先 `NOT VALID` 再 `VALIDATE CONSTRAINT` 分步上线（`NOT VALID` 自 9.1 起用于外键、9.2 起扩展到 CHECK）。上游该禁令的动机（MySQL 时代的实例扩展性与复制约束）在 PG 上不成立。
4. **命名「不含数字」vs 分片/日期命名（[2.1.1-3] vs [2.1.2-5]、[2.1.7-10]）**：上游两条同为【强制】级的条款自相矛盾——[2.1.1-3] 要求「名称中没有数字，只有英文字母」，[2.1.2-5] 却把分库名定义为「库通配名_编号，编号从 0 开始递增，比如 northwind_001」；[2.1.7-10] 要求日志与报表类数据按日期分表，日期后缀同样含数字；而 [2.1.2-1] 明文要求遵守 2.1.1 的全部一般命名规则，使该矛盾构成直接违反上位条款。PG 结论：把 [2.1.1-3] 收敛为对「业务词根」的约束——词根只用英文字母、不含数字；编号后缀属显式例外，且只限两类：①分片序号 `<库通配名>_<编号>`，编号从 0 起递增，如 `northwind_0`；②日期时间后缀，如按日期分表的 `log_2026_10`。除这两类后缀，标识符仍不得出现数字；例外后缀也不得使标识符以数字开头（PG 中未加引号的标识符必须以字母或下划线开头，`2026_log` 不合法，加引号后大小写敏感、必须始终带引号）。

## 规范建表语句示例（PG 版）

```sql
CREATE SCHEMA IF NOT EXISTS app;

CREATE TABLE app.user_account (
    id            bigint       GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id       bigint       NOT NULL,
    username      text         NOT NULL,
    email         text         NOT NULL,
    nickname      text         NOT NULL,
    avatar        text         NOT NULL,
    birthday      date         NOT NULL,
    gender        smallint     NOT NULL DEFAULT 0,
    intro         text,
    resume_url    text         NOT NULL,
    register_ip   inet         NOT NULL,
    review_status smallint     NOT NULL,
    create_time   timestamptz  NOT NULL DEFAULT now(),
    update_time   timestamptz  NOT NULL DEFAULT now(),
    CONSTRAINT uk_user_account_user_id UNIQUE (user_id),
    CONSTRAINT ck_user_account_review_status CHECK (review_status IN (1, 2, 3, 4)),
    CONSTRAINT ck_user_account_gender CHECK (gender IN (0, 1, 2))
);

COMMENT ON TABLE app.user_account IS '用户基本信息';
COMMENT ON COLUMN app.user_account.review_status IS '审核状态：1-通过，2-审核中，3-未通过，4-尚未提交审核';

CREATE INDEX idx_user_account_username ON app.user_account (username);
CREATE INDEX idx_user_account_create_status
    ON app.user_account (create_time DESC, review_status) INCLUDE (nickname);
```

说明：表名未沿用上游示例中的 `user`，因为在 PG 中 `user` 是保留关键字、必须加引号使用；改用 `user_account` 保持单数与自解释（对应 [2.1.3-2]、[2.1.4-3]）。

## DDL 检查清单

1. 标识符全小写、无空格、长度不超过 32 个字符；除分片序号与日期时间后缀（见「条款冲突裁决」第 4 条）外不含数字（[2.1.1-1] ~ [2.1.1-7]）。
2. 表名与字段名单数、自解释、非保留字、不与表名同名（[2.1.3-2]、[2.1.4-2] ~ [2.1.4-6]）。
3. 主键为 `id bigint GENERATED BY DEFAULT AS IDENTITY`，主键值不更新；业务键有独立 UNIQUE 约束（[2.1.3-7]、[2.1.6-1]）。
4. 表与列均有 `COMMENT ON` 注释（[2.1.3-6]）。
5. 字段尽量 `NOT NULL` + `DEFAULT`；`CHECK` 约束覆盖枚举语义（[2.1.3-9]、[2.1.5-4]）。
6. 时间列一律 `timestamptz`，IP 列一律 `inet`，金额列一律 `numeric(p,s)`（[2.1.5-3]、[2.1.5-6]、[2.1.5-8]）。
7. IP、金额、大文本列不随热点查询一起 `select`（[2.1.3-10]、[2.1.5-5]）。
8. 索引以 `pk_`/`uk_`/`idx_` 前缀命名，联合索引高区分度列在前，无冗余索引，单表索引不超过 5 个（[2.1.6-2]、[2.1.6-5]、[2.1.6-6]、[2.1.6-8]）。
9. 分区表分区键在索引首列，SQL 带分区键，分区创建与清理策略已定（[2.1.7-1]、[2.1.7-3]、[2.1.7-4]）。
10. database 与客户端编码统一为 UTF8，collation 一致（[2.1.8-1]、[2.1.8-2]）。
11. 大表变更拆分为 `CREATE INDEX CONCURRENTLY`、`NOT VALID` + `VALIDATE CONSTRAINT`、低峰期执行（[2.1.3-13]、[2.1.7-6]）。

## MySQL 与 PostgreSQL 差异速查表

| 主题 | 上游 MySQL 做法 | PG 做法 |
| --- | --- | --- |
| 自增主键 | 上游 MySQL 用 `auto_increment` 列 | `bigint GENERATED BY DEFAULT AS IDENTITY`（≥10），不用 `serial` |
| 存储模型 | 上游要求指定 InnoDB/MyISAM 等存储引擎 | 只有堆表 + MVCC + TOAST；物理隔离用 tablespace 或分区 |
| 字符集 | 上游 MySQL 用 utf8/utf8mb4，且需逐库逐表声明 | 统一 UTF8，编码/排序规则继承自 database，特殊排序用列级 collation |
| 整数类型 | 上游 MySQL 有 tinyint/mediumint 等窄类型 | 用 `smallint`/`int`/`bigint` |
| IP 存储 | 上游 MySQL 用 int + inet_aton/inet_ntoa、应用层 ip2long | 原生 `inet` 类型，可直接比较与建索引 |
| 金额 | 上游 MySQL 用 int 存「分」，规避 decimal | `numeric(p,s)` 精确十进制，无精度损失 |
| 时间 | 上游 MySQL 用 timestamp/datetime，或用 int + unix_timestamp() | `timestamptz` 为默认；`timestamp` 需写理由 |
| 索引类型 | 上游 MySQL 强制 BTREE | btree 为默认，另有 gin/gist/brin/hash（hash 仅等值），支持 partial index 与 `INCLUDE`（≥11） |
| 计划干预 | 上游 MySQL 禁用 hint 但也依赖优化器 | PG 无 hint 语法，可用 `pg_hint_plan` 扩展或改写 SQL |
| upsert | 上游 MySQL 的 on duplicate key update 被禁 | `INSERT ... ON CONFLICT DO UPDATE`（≥9.5）/ `DO NOTHING` |
| 带 limit 的更新 | 上游 MySQL 高危禁用 | PG 语法不支持，用 CTE + `ctid` 或 `FOR UPDATE SKIP LOCKED` 分批 |
| 隔离与锁 | 上游 MySQL 有间隙锁，建议 repeatable-read | `read committed` 默认，`repeatable read` 为快照隔离，SSI 需重试；无间隙锁 |
| 外键/视图/触发器 | 上游 MySQL 一律禁用 | 声明式外键默认启用，只读视图可用，触发器与过程需评审 |
| 复制与读路由 | 上游 MySQL 写主读从，注意主从延迟 | 流复制/逻辑复制，`synchronous_commit` 与只读副本路由由中间件负责 |
| 运维观测 | 上游 MySQL 用 show create table 等 | `pg_dump -s`、`information_schema`、`psql \d+`、`pg_relation_size()` |
