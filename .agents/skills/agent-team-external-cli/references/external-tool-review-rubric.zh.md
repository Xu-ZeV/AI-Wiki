# 外部委托跨模型评审 rubric

**使用者**：以对抗性评审者身份工作的 Codex 原生子代理（实现者与评审者必须是不同模型）
**用途**：依据任务规格，评估由**另一个模型**产出的代码改动
**版本**：1.0

---

## 概述

本 rubric 用于"一个模型评审另一个模型写出的代码"的场景。
评审者与实现者**没有共享上下文**：它只看得到 diff、规格说明和这份 rubric。评审者必须是**对抗性**的——在得到证据之前，假定一切都不能正常工作。

## 判定

| 判定 | 含义 | 标准 |
|------|------|------|
| **PASS** | 代码满足规格 | 全部验收标准已满足，未发现 BLOCKING 问题 |
| **FAIL** | 代码不满足规格 | 发现一个或多个 BLOCKING 问题 |

## 问题分类

| 分类 | 含义 | 影响 |
|------|------|------|
| **BLOCKING** | 违反契约、缺失需求、功能损坏 | 导致 FAIL |
| **WARNING** | 风格问题、小幅改进、非关键疑虑 | 不导致 FAIL |

## 评审清单

评审者**必须**逐项对照规格检查：

### 1. 验收标准覆盖
- [ ] 规格中的每一条验收标准都有对应代码
- [ ] 没有哪条标准只被部分实现或被占位桩（stub）代替

### 2. 功能正确性
- [ ] 逻辑正确处理了规格中陈述的需求
- [ ] 规格中提到的边界情况已被处理
- [ ] 错误路径产生合理行为（不是崩溃，也不是静默失败）

### 3. 测试覆盖
- [ ] 新增/改动的功能有对应测试
- [ ] 测试真的在断言验收标准（不是只做冒烟测试）
- [ ] 若把实现删掉测试会失败（不是同义反复的测试）

### 4. 范围纪律
- [ ] 改动限于规格要求之内（没有镀金）
- [ ] 没有无关的重构或格式化改动
- [ ] 没有在规格未说明理由的情况下引入新依赖

### 5. 安全性（违反即为 BLOCKING）
- [ ] 没有硬编码的密钥、凭证或 API Key
- [ ] 没有命令注入、SQL 注入或 XSS 向量
- [ ] 没有不安全的文件操作（路径穿越、全局可写文件）

## 证据要求

每一条发现（BLOCKING 或 WARNING）**必须**包含：

- **文件与行号引用**：`src/auth/login.ts:42`
- **问题是什么**：对问题的具体描述
- **规格要求是什么**：引用相关的验收标准原文

## 输出格式

评审者应按以下格式输出：

```markdown
## 跨模型评审：[task-id]

### 判定：PASS | FAIL

### 验收标准核对
| # | 标准 | 判定 | 证据 |
|---|------|------|------|
| 1 | [标准原文] | PASS/FAIL | [file:line 引用] |

### BLOCKING 问题
1. **[问题标题]**：[描述]（`file:line`）—— 规格要求："[引用的标准原文]"

### WARNING 问题
1. **[问题标题]**：[描述]（`file:line`）
```

## 与 Codex 原生子代理的配合

- 本 rubric 的全文由编排者放进评审子代理的 `spawn_agent(message=...)` 中，评审子代理默认 `fork_context=false`，因此它只能看到 prompt 里的 diff、规格与本 rubric。
- 评审子代理**只读**：不修改任何文件，只输出结论与发现。
- 评审子代理给出的 PASS/FAIL 只是建议，**最终裁决权在编排者**：编排者独立跑质量门后再定论。
- 实现者与评审者必须是不同模型；只有两个模型可用时，第二轮换回实现者模型必须更换 `reasoning_effort` 并使用全新上下文，且必须标注这是**同模型降级方案**，不能替代第一轮的异模型评审。
