# Karpathy 的 LLM Wiki 模式 — 原始参考

来源：https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f

## 核心洞察

“维基是一个持久的、复合的工件。知识被编译一次，然后保持最新，而不是在每次查询时重新派生。”

人类整理资源并提出问题； LLM维护知识体系。 Obsidian 成为 IDE，LLM 成为程序员，wiki 成为代码库。

## 为什么这比 RAG 更好

传统的 RAG 重新发现每个查询的知识 - 它搜索原始来源，提取相关块，并从头开始综合答案。 LLM Wiki 将知识一次编译到维护的页面中，因此查询会命中预先合成的交叉引用内容。

## 关键操作

|运营|它有什么作用 |何时使用 |
|---|---|---|
| **摄取** |阅读新来源、提取关键信息、更新 10-15 个 wiki 页面、保持一致性 |当新文件到达时 |
| **查询** |通过引用回答针对已编译维基的问题 |当用户询问某事时 |
| **棉绒** |识别矛盾、孤立页面、陈旧声明、缺失交叉引用 |定期保养|

## 推荐工具

- **Obsidian** — 用于浏览和探索 wiki 的 IDE
- **Web Clipper** — 用于将文章转换为 Markdown 的浏览器扩展
- **Marp** — 来自 wiki 内容的基于 Markdown 的幻灯片
- **Dataview** — 用于查询页面元数据的 Obsidian 插件
- **qmd** — 具有 BM25/矢量混合搜索的本地搜索引擎

## 应用

- 个人追踪（目标、心理、自我提升）
- 研究（在数周/数月内建立全面的理解）
- 书籍注释（带有人物、主题、情节连接的同伴维基）
- 团队/业务（来自 Slack 线程的 wiki、会议记录）
- 尽职调查、竞争分析、旅行计划

## 值得了解的社区扩展

- **出处跟踪** — 记录哪些源文件产生了每个声明，通过内容哈希检测陈旧性
- **分层继承** - 父子页面关系而不是平面索引
- **决策记录** — 记录 wiki 演变的原因，而不仅仅是发生了什么变化
- **两层LLM** - 敏感数据的本地模型，其余的云模型
- **图形数据库** — 类型本体而不是 Markdown 链接
