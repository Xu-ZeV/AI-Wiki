# 输出限制和消费者截断

## 上下文窗口不对称

像 Gemini 这样的模型具有大量的输入上下文窗口（最多 200 万个token），但严格限制输出限制（通常为 8,000 个token）。当模型估计完整的响应将超出其输出预算时，它会先发制人地压缩或汇总输出，而不是冒着突然中断的风险。

这就产生了一个悖论：模型可以读取大量输入，但无法按比例响应，导致复杂任务的系统信息丢失。

## 消费者中间件问题

面向消费者的应用程序（gemini.google.com、标准 ChatGPT 层）在模型的固有限制之上应用了额外的软件级截断。该中间件会默默地截断对话历史记录和上传的文件，以降低免费和低级用户的计算成本。

关键机制：

- **历史记录上限：** 许多消费者界面将活动对话历史记录上限限制为大约 32,000 个token，无论模型的实际容量如何。
- **上下文修剪：** 大型系统指令或保存的个人上下文会消耗原本可用于对话的token，从而有效地缩小工作窗口。
- **基于检索的召回：** 消费者应用程序通常使用检索机制来有选择地注入保存的上下文，这意味着模型经常删除在会话早期给出的指令。

## 开发者平台差异

直接 API 访问和开发者平台（Google AI Studio、OpenAI API Playground）完全绕过消费者中间件。这些环境提供：

- 完整的上下文窗口访问，无需隐藏截断
- 完全控制发电参数
- 没有基于用户级别的动态限制
- 无需中间件干扰即可处理复杂的提示结构

实际差异是显着的：通过消费者接口生成截断输出的同一模型在通过直接 API 端点访问时将生成完整的、未删节的响应。

## 终端和 CLI 集成

专门构建的 CLI 工具（Gemini CLI、Claude Code、第三方包装器）为避免截断提供了额外的优势：

|访问方式|上下文处理 |截断风险|参数控制|
|:---|:---|:---|:---|
|消费者网络应用程序 |积极修剪，32K 上限 |高|有限公司|
|开发者平台（AI Studio）|完整上下文，无隐藏切片 |低|完整|
|直接API |完整上下文，原始访问 |最小 |完整|
|具有本地模型的 CLI 工具 |没有公司对齐过滤器 |无 |完整|
