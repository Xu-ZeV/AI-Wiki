### 目的

解决一个稳定的目标，运行两次独立的评估，综合设计批评，保留快照，并询问用户下一步要改进什么。聊天响应是主要交付成果；快照是未来命令的存档/积压。

### 硬不变量

- 评估 A（设计审查）和评估 B（检测器/浏览器证据）都是必需的。
- 评估 A 必须在检测器结果进入父综合上下文之前完成。检测器的输出是确定性的，但它仍然锚定判断。
- 如果子代理不可用，则按顺序回退：首先完成并记录评估 A，然后运行评估 B，然后综合。
- 跳过的检测器是一次失败的批评运行，除非 `detect.mjs` 在真正的尝试后丢失或崩溃。
- 可见目标需要浏览器检查（如果可用）。
- 任何仅为批判可视化而启动的本地服务器必须在后台运行，具有记录的停止方法，并在最终报告之前停止，除非用户要求保留它。
- 除非脚本注入成功并且检测器在页面中运行，否则不要声明存在用户可见的覆盖层。

### 设置

1. **将目标解析为具体的文件路径或 URL。当两者标识相同表面时，优先选择源路径而不是开发服务器 URL；端口会漂移，但路径不会。
   - “主页”-> `site/pages/index.astro` 或 `index.html`
   -“设置模式”->主组件文件
   - “本页” -> 当前 URL 或源文件
2. **计算段头**：
   ```bash
   node .agents/skills/impeccable/scripts/critique-storage.mjs slug "<resolved-path-or-url>"
   ```
   保留它。如果命令以非零值退出，则跳过此运行的持久性和趋势，但继续批评。
3. **读取`.impeccable/critique/ignore.md`**（如果存在）。默默地丢弃匹配的结果；它是唯一的先前运行输入批判消耗。

### 评估编排

如果可能，将评估 A 和评估 B 委托给单独的子代理。他们不能看到彼此的输出。在综合之前不要向用户显示结果。

Codex 子代理门：
- 如果 `spawn_agent` 被暴露并且用户明确允许子代理、委派或并行代理工作，则立即生成 A 和 B。
- 如果 `spawn_agent` 被暴露，但用户没有明确允许子代理，请仅询问一次：“Impeccable critique 旨在运行两个独立的子代理来进行非锚定评估。我可以使用子代理来进行此批评吗？”然后停止，直到用户回答。
- 如果允许，生成 A 和 B。如果拒绝，则按顺序运行并报告 `Assessment independence: degraded (sub-agents declined by user)`。
- 若`spawn_agent`未暴露，请勿询问；按顺序运行并报告 `Assessment independence: degraded (spawn_agent unavailable in this session)`。
- 如果获得许可后生成失败，则依次运行并报告 `Assessment independence: degraded (sub-agent spawn failed: <exact error>)`。
更喜欢 `fork_context: false` 以及包含 cwd、目标、实时 URL、引用、产品上下文和输出合同的独立提示。如果使用 `fork_context: true`，则省略 `agent_type`、`model` 和 `reasoning_effort`。

如果浏览器自动化可用，则每个评估都会创建自己的新选项卡。切勿重复使用现有选项卡，即使它已位于正确的 URL 处。

### 评估 A：设计审查

当浏览器自动化可用时，阅读相关源文件并目视检查实时页面。像设计总监一样思考。

评价：
- **AI slop**：有人会立即相信“AI 创造了这个”吗？检查家长的所有“不要”指导 无可挑剔的技能。
- **整体设计**：层次结构、IA、情感契合、可发现性、构图、排版、颜色、可访问性、状态、副本和边缘情况。
- **认知负荷**：请参阅下面的[认知负荷评估](#cognitive-load-assessment) 部分；报告清单失败和决策点，并具有 >4 个可见选项。
- **情感之旅**：高峰结束法则、情绪低谷、高风险时刻的安心。
- **尼尔森启发式**：请参阅下面的[启发式评分指南](#heuristics-scoring-guide) 部分；所有 10 个启发式得分为 0-4。

返回：AI 错误判决、启发式分数、认知负荷、情感旅程、2-3 个优势、3-5 个优先问题、角色危险信号、次要观察结果和挑衅性问题。

### 评估 B：检测器 + 浏览器证据

运行捆绑的检测器和浏览器可视化证据。评估 B 是强制性的，并且必须与评估 A 保持隔离，直到两者都完成。

CLI 扫描：
```bash
node .agents/skills/impeccable/scripts/detect.mjs --json [target]
```

- 将标记文件/目录传递为 `[target]`；不要传递纯 CSS 文件。
- 对于 URL，跳过 CLI 扫描并使用浏览器可视化。
- 对于非常大的树（500+可扫描文件），缩小范围或询问。
- 退出代码 0 = 干净； 2 = 调查结果。
- 如果检测器入口点丢失或无法加载，则报告确定性扫描不可用并继续浏览器/手动审核。

当浏览器自动化可用时，可视目标需要浏览器可视化。对本地文件使用 localhost dev/static URL；避免“file://`”，除非可用的浏览器明确支持此工作流程。叠加流程：

1. 创建一个新选项卡并导航。
2. 通过设置 `document.title` 并附加 `<script>` 标签来预检可变注入。只读评估 API 不算在内。
3. 如果突变不可用，则跳过实时服务器、浏览器呈现和注入；报告后备信号。
4. 如果突变可用，则启动 `node .agents/skills/impeccable/scripts/live-server.mjs --background`，显示浏览器（如果支持），标记 `[Human]`，滚动顶部，注入 `http://localhost:PORT/detect.js`, wait 2-3 seconds, read `impeccable` 控制台消息，然后停止实时服务器。
5. 对于多视图目标，注入 3-5 个代表性页面。

Codex 浏览器注意：使用浏览器技能。不要在 `file://`. Only call `visibility.set(true)` after mutable script injection is confirmed for the `[Human]` overlay path; verify with `get()`. Use `tab.dev.logs({ filter: "impeccable" })` for console results. Its Playwright `evaluate(...)` 表面上花费浏览器尝试只读；不要依赖它进行突变。

返回：CLI 结果 JSON/计数、浏览器控制台结果（如果适用）、误报以及带有具体原因的跳过/失败的浏览器步骤。

评估 B 返回可用的 CLI 结果后，重复使用它们。除非评估 B 失败、被截断或省略计数、规则名称或文件位置，否则请勿在父级中重新运行 `detect.mjs`。

Codex 故障统计：最终运行注释必须包括目标 slug、忽略列表、评估独立性、CLI 检测器、浏览器可见性、覆盖注入、实时服务器清理、临时文件清理以及使用的任何后备信号。报告组装后，请勿运行存储库状态检查、后期 API 探索或不相关的验证。

### 生成综合批评报告

将两项评估综合成一份报告。不要简单地连接。将结果编织在一起，注意LLM审查和检测器一致的地方，检测器发现LLM错过的问题的地方，以及检测器发现的误报的地方。

聊天响应是面向用户的主要交付成果。在聊天中提出以下完整的结构化批评；不要用摘要和链接替换它。持久化快照只是后续命令的存档/积压。

Codex 最终答案注释：`$impeccable critique` 会生成报告工件，因此最终的聊天响应应有意超过通常的简洁结束风格。不要将最终回复标题为“批评摘要”，除非用户明确要求提供摘要。

像设计总监一样构建您的反馈：

#### 反模式判决

**从这里开始。** 这看起来是人工智能生成的吗？

**LLM评估**：您自己对AI slop的评估告诉我们。涵盖整体美感、布局千篇一律、通用构图、错失个性机会。

**确定性扫描**：总结自动检测器发现的内容，包括计数和文件位置。记下检测器发现的您错过的任何其他问题，并标记任何误报。

**视觉覆盖**（如果注入成功）：告诉用户覆盖现在在浏览器的 **[Human]** 选项卡中可见，突出显示检测到的问题。总结控制台输出报告的内容。如果尝试浏览器可视化但注入失败，则说明没有可靠的用户可见覆盖可用，并报告回退信号。

#### 总体印象
简短的直觉反应：什么有效，什么无效，以及最大的机会。

#### 什么有效
突出显示 2-3 件做得好的事情。具体说明它们为什么起作用。

#### 优先问题
3-5 个最具影响力的设计问题，按重要性排序。

对于每个问题，使用 **P0-P3 严重性**进行标记（请参阅下面的[问题严重性](#issue-severity-p0p3) 了解定义）：
- **[P?] 什么**：清楚地指出问题
- **为什么重要**：这如何伤害用户或破坏目标
- **修复**：该怎么办（具体）
- **建议的命令**：哪个命令可以解决这个问题（来自：$完美适应，$完美动画，$完美审计，$完美大胆，$完美澄清，$完美着色，$完美批评，$完美喜悦，$完美蒸馏，$完美文件，$完美硬化，$完美布局，$完美船上， $无可挑剔的优化，$无可挑剔的超速，$无可挑剔的抛光，$无可挑剔的安静，$无可挑剔的形状，$无可挑剔的排版)

#### 角色危险信号
> *请参阅下面的[角色参考](#persona-based-design-testing)。*

自动选择与此界面类型最相关的 2-3 个角色（使用参考中的选择表）。如果 `AGENTS.md` 包含 `impeccable init` 中的 `## Design Context` 部分，还可以根据受众/品牌信息生成 1-2 个项目特定角色。

对于每个选定的角色，浏览主要用户操作并列出发现的特定危险信号：

**Alex（高级用户）**：未检测到键盘快捷键。表单需要点击 8 次才能执行主要操作。强制模式入职。遗弃风险高。

**乔丹（新手）**：侧边栏中仅包含图标导航。错误消息中的技术术语（“404 Not Found”）。没有可见的帮助。将在第 2 步放弃。

具体一点。说出每个角色失败的确切元素和交互。不要写通用的角色描述；写下他们遇到的困难。

#### 小观察
关于值得解决的小问题的快速说明。

#### 需要考虑的问题
具有挑战性的问题可能会带来更好的解决方案：
- “如果主要行动更加突出怎么办？”
——“需要这么复杂的感觉吗？”
- “这个的自信版本会是什么样子？”

#### 运行笔记
保持这个紧凑。包括目标 slug 的状态、忽略列表、评估独立性、CLI 检测器、浏览器可见性、覆盖注入、实时服务器清理和临时文件清理。对于失败或跳过的步骤，给出具体观察到的原因和使用的后备信号。在最终的聊天响应中，还包括持久化运行后的快照写入和趋势读取状态。

Codex 运行笔记仅供最终讨论。不要将此部分包含在持久化快照正文中，因为持久化、趋势读取和临时清理发生在快照写入之后，否则会归档过时状态，例如“持久化后待处理”。

**记住**：
- 直接点。模糊的反馈浪费了每个人的时间。
- 具体一点。 “提交按钮”，而不是“某些元素”。
- 说出问题所在以及为什么它对用户很重要。
——提出具体建议。完全删除“考虑探索……”。
- 无情地确定优先顺序。如果一切都很重要，那么什么都不重要。
- 不要软化批评。开发者需要诚实的反馈来交付出色的设计。

### 保留快照

上述报告完成后，将其写入 `.impeccable/critique/`，以便用户可以参考，这样 `$impeccable polish` 就可以在无需复制粘贴的情况下找出优先级问题。

如果安装段为空（模糊或根级目标），请跳过此步骤。

1. **将正文写入临时文件**，以便您可以将其通过管道传递给帮助程序。使用完整的批评报告（启发式表、反模式判决、优先问题、角色危险信号、次要观察结果和问题），但在稍后出现的“询问用户”/“建议操作”部分之前停止。

   Codex：从临时正文文件中排除运行注释；运行注释只是最终聊天，因为持久性、趋势读取和临时清理发生在快照写入之后。

2. **通过 `IMPECCABLE_CRITIQUE_META` (JSON) 传递结构化元数据**，然后运行写入命令：
   ```bash
   IMPECCABLE_CRITIQUE_META='{"target":"<user phrasing>","total_score":<n>,"p0_count":<n>,"p1_count":<n>}' \
     node .agents/skills/impeccable/scripts/critique-storage.mjs write <slug> <body-file>
   ```
   助手打印它所写的绝对路径。

3. **在写入尝试完成后删除临时正文文件**，无论写入成功还是失败。如果删除失败，请在最终输出中简要提及 `temp-file cleanup failed: <reason>`，但不要阻止批评。

4. **阅读趋势**了解背景：
   ```bash
   node .agents/skills/impeccable/scripts/critique-storage.mjs trend <slug> 5
   ```
   这将返回最后 5 个 frontmatter 条目（包括您刚刚编写的条目）的 JSON 数组。

5. **在用户可见的输出中附加一行**，位于报告之后、问题之前：

   > **`<slug>` 的趋势（最后 5 次运行）：24 → 28 → 32 → 29 → 32**
   > 写为 `.impeccable/critique/<filename>`。

   如果这是 slug 的第一次运行，则趋势只是一个分数；这么说：“第一次运行这个目标，还没有趋势。”

这是一劳永逸的。不要向用户显示助手的 JSON 输出；只有人类可读的趋势线和书面路径。这里的失败不应该阻塞其余的流程；打印错误并继续。

### 询问用户

**展示发现后**，根据实际发现提出有针对性的问题。停止并使用 Codex 的结构化用户输入/问题工具（如果可用）；如果无法推断，请直接在聊天中询问以澄清您无法推断的内容。这些答案将影响行动计划。

按照以下思路提出问题（适应具体的调查结果；不要问一般性问题）：

1. **优先方向**：根据发现的问题，询问当前哪个类别对用户最重要。例如：“我发现视觉层次、颜色使用和信息过载方面存在问题。我们应该首先解决哪个领域？”提供前 2-3 个问题类别作为选项。

2. **设计意图**：如果批评发现色调不匹配，询问是否是故意的。例如：“界面给人一种冷静和企业的感觉。这是预期的基调，还是应该感觉更温暖/更大胆/更有趣？”根据解决所发现问题的方法，提供 2-3 个色调方向作为选项。

3. **范围**：询问用户想要承担多少。例如：“我发现了 N 个问题。想要解决所有问题，还是专注于前 3 个问题？”提供范围选项，例如“仅前 3 个问题”、“所有问题”、“仅关键问题”。

4. **限制**（可选；仅询问是否相关）：如果调查结果涉及许多领域，询问是否有任何限制。例如：“任何部分都应该保持原样吗？”这可以防止计划触及用户认为已完成的事情。

**提问规则**：
- 每个问题都必须参考报告中的具体调查结果。永远不要问“你的观众是谁？”问题。
- 最多 2-4 个问题。尊重用户的时间。
- 提供具体的选项，而不是开放式的提示。
- 如果发现很简单（例如，只有 1-2 个明确的问题），请跳过问题并直接转到建议的操作。

Codex 最终问题门：用户可见的响应必须包含有针对性的问题或明确指出 `Questions skipped: <reason>`，因为结果很简单。每个问题必须包含 2-3 个与实际批评结果相关的具体答案选项。不要仅以开放式问题结束。

### 认知负荷评估

认知负荷是使用界面所需的总脑力劳动。超负荷的用户会犯错误、感到沮丧并离开。此参考有助于识别和修复认知超载。

---

#### 三种类型的认知负荷

##### 内在负载：任务本身
用户尝试做的事情固有的复杂性。你无法消除它，但你可以构建它。

**管理方式**：
- 将复杂的任务分解为离散的步骤
- 提供脚手架（模板、默认值、示例）
- 渐进式披露：显示现在需要的内容，隐藏其余的
- 将相关决策分组在一起

##### 额外负载：糟糕的设计
由于设计选择不当而造成的脑力劳动。 **无情地消除这个。**这纯粹是浪费。

**常见来源**：
- 令人困惑的导航需要思维导图
- 不明确的标签迫使用户猜测含义
- 视觉混乱争夺注意力
- 阻碍学习的不一致模式
- 用户意图和结果之间不必要的步骤

##### Germane 负载：学习努力
花费脑力去建立理解。这是*好的*认知负荷；它通向精通。

**通过以下方式支持**：
- 渐进式披露，逐渐揭示复杂性
- 奖励学习的一致模式
- 确认正确理解的反馈
- 入职培训通过行动进行教学，而不是文字墙

---

#### 认知负荷检查表

根据这 8 项评估界面：

- [ ] **单一焦点**：用户能否在不干扰竞争元素的情况下完成主要任务？
- [ ] **分块**：信息是否以可消化的组形式呈现（每组≤4 个项目）？
- [ ] **分组**：相关项目是否在视觉上分组在一起（邻近度、边框、共享背景）？
- [ ] **视觉层次结构**：屏幕上最重要的内容是否立即清晰？
- [ ] **一次一件事**：用户可以在转向下一个决策之前专注于单个决策吗？
- [ ] **最少选择**：决策是否简化（在任何决策点≤4 个可见选项）？
- [ ] **工作记忆**：用户是否需要记住上一屏幕的信息才能对当前屏幕进行操作？
- [ ] **渐进式披露**：复杂性是否仅在用户需要时才披露？

**评分**：计算失败的项目。 0-1 次失败 = 认知负荷低（好）。 2-3 = 中等（很快就会解决）。 4+ = 高认知负荷（需要关键修复）。

---

#### 工作记忆规则

**人类工作记忆中可以同时容纳≤4个项目**（米勒定律，Cowan 修订，2001）。

在任何决策点，计算用户必须同时考虑的不同选项、操作或信息的数量：
- **≤4 项**：在工作记忆限制内，可管理
- **5–7 项**：突破界限；考虑分组或渐进式披露
- **8+ 项目**：超载；用户会跳过、误点击或放弃

**实际应用**：
- 导航菜单：≤5 个顶级项目（将其余项目分组到明确的类别下）
- 表单部分：视觉中断前每组 ≤4 个可见字段
- 操作按钮：1 个主要按钮，1–2 个辅助按钮，其余按钮分组在菜单中
- 仪表板小部件：≤4 个关键指标无需滚动即可可见
- 定价等级：≤3个选项（更多原因分析瘫痪）

#### 常见的认知负荷违规

##### 1.选项之墙
**问题**：一次呈现 10 多个选择，没有层次结构。
**修复**：分组、突出推荐、使用渐进式披露。

##### 2.记忆桥
**问题**：用户必须记住步骤 1 中的信息才能完成步骤 3。
**修复**：保持相关上下文可见，或在需要的地方重复它。

##### 3.隐藏的导航
**问题**：用户必须构建事物所在位置的心理地图。
**修复**：始终显示当前位置（面包屑、活动状态、进度指示器）。

##### 4.行话障碍
**问题**：技术或领域语言迫使翻译工作。
**修复**：使用简单的语言。如果领域术语不可避免，请内联定义它们。

##### 5. 视觉本底噪声
**问题**：每个元素都有相同的视觉权重；没有什么突出的。
**修复**：建立清晰的层次结构：一个主要元素，2-3 个次要元素，其他一切都静音。

##### 6. 不一致的模式
**问题**：类似的操作在不同的地方会有不同的效果。
**修复**：标准化交互模式。相同类型的操作 = 相同类型的 UI。

##### 7. 多任务需求
**问题**：界面需要处理多个同时输入（阅读+决定+导航）。
**修复**：对步骤进行排序。让用户一次只做一件事。

##### 8. 上下文切换
**问题**：用户必须在屏幕/选项卡/模式之间跳转才能收集单个决策的信息。
**修复**：将每个决策所需的信息放在一起。减少来回。

### 启发式评分指南

对尼尔森的 10 个可用性启发法中的每一个进行评分，评分范围为 0-4。说实话：4 意味着真正优秀，而不是“足够好”。

#### 尼尔森的 10 条启发法

##### 1.系统状态可见性

通过及时、适当的反馈让用户了解正在发生的事情。

**检查**：
- 在异步操作期间加载指标
- 确认用户操作（保存、提交、删除）
- 多步骤流程的进度指示器
- 导航中的当前位置（面包屑、活动状态）
- 表单验证反馈（内联，不仅仅是提交时）

**评分**：
|分数 |标准|
|-------|----------|
| 0 |没有反馈；用户正在猜测发生了什么|
| 1 |罕见的反馈；大多数行动不会产生明显的反应
| 2 |部分的;一些国家通报，但仍存在重大差距|
| 3 |好的;大多数操作都会给出明确的反馈，但存在细微的差距
| 4 |出色的;每一次行动确认，进步始终可见 |

##### 2.系统与现实世界的匹配

说用户的语言。遵循现实世界的惯例。信息以自然、逻辑的顺序出现。

**检查**：
- 熟悉的术语（没有无法解释的行话）
- 符合用户期望的逻辑信息顺序
- 可识别的图标和隐喻
- 适合目标受众领域的语言
- 自然的阅读流程（从左到右，从上到下优先）

**评分**：
|分数 |标准|
|-------|----------|
| 0 |纯粹的技术术语，对用户来说很陌生|
| 1 |大多令人困惑；需要领域专业知识才能导航 |
| 2 |混合；一些简单的语言，一些行话泄漏
| 3 |大部分是自然的；偶尔术语需要上下文|
| 4 |始终流利地说用户的语言 |

##### 3. 用户控制和自由

用户需要一个明确的“紧急出口”来摆脱不需要的状态，而无需进行长时间的对话。

**检查**：
- 撤消/重做功能
- 取消表单和模式上的按钮
- 清晰导航返回安全（主页、上一个）
- 清除过滤器、搜索、选择的简单方法
- 摆脱冗长或多步骤的流程

**评分**：
|分数 |标准|
|-------|----------|
| 0 |用户被困；不刷新就没有出路|
| 1 |退出困难；必须找到隐蔽的逃生路径|
| 2 |一些出口；主要流程有逃逸，边缘情况没有|
| 3 |控制性好；用户可以退出并撤消大多数操作 |
| 4 |完全控制；随处撤消、取消、返回和退出 |

##### 4. 一致性和标准

用户不应该怀疑不同的词语、情况或动作是否意味着同一件事。

**检查**：
- 整个界面的术语一致
- 相同的行动在任何地方都会产生相同的结果
- 遵循平台约定（标准 UI 模式）
- 视觉一致性（颜色、排版、间距、组件）
- 一致的交互模式（相同的手势=相同的行为）

**评分**：
|分数 |标准|
|-------|----------|
| 0 |处处不一致；感觉像是不同的产品缝合在一起|
| 1 |许多不一致之处；相似的事物看起来/行为不同 |
| 2 |部分一致；主要流程一致，细节有所不同|
| 3 |基本一致；偶尔出现偏差，没有什么令人困惑的|
| 4 |完全一致；内聚的系统，可预测的行为 |

##### 5. 错误预防

比好的错误消息更好的是能够从一开始就防止出现问题的设计。

**检查**：
- 破坏性操作（删除、覆盖）之前的确认
- 防止无效输入的约束（日期选择器、下拉菜单）
- 智能默认设置可减少错误
- 清晰的标签，防止误解
- 自动保存和草稿恢复

**评分**：
|分数 |标准|
|-------|----------|
| 0 |容易犯错误；任何地方都没有护栏|
| 1 |保障措施很少；一些输入已验证，但大多数未验证 |
| 2 |部分预防；发现常见错误，但边缘情况出现问题 |
| 3 |良好的预防；主动阻止大多数错误路径 |
| 4 |出色的;通过智能约束几乎不可能出现错误|

##### 6. 识别而不是回忆

最小化内存负载。使对象、操作和选项可见或易于检索。

**检查**：
- 可见选项（不隐藏在隐藏菜单中）
- 需要时的上下文帮助（工具提示、内联提示）
- 最近的项目和历史记录
- 自动完成和建议
- 图标上的标签（不仅仅是图标导航）

**评分**：
|分数 |标准|
|-------|----------|
| 0 |大量记忆；用户必须记住路径和命令|
| 1 |主要是回忆；许多隐藏的功能，很少可见的线索|
| 2 |一些辅助工具；主要操作可见，次要功能隐藏 |
| 3 |良好的认可度；大多数东西都是可发现的，几乎不需要内存|
| 4 |一切皆可发现；用户永远不需要记住|

##### 7. 使用的灵活性和效率

新手看不见的加速器可以加速专家交互。

**检查**：
- 常用操作的键盘快捷键
- 可定制的界面元素
- 最近的项目和收藏夹
- 批量/批量操作
- 高级用户功能不会使基础变得复杂

**评分**：
|分数 |标准|
|-------|----------|
| 0 |一条僵硬的道路；没有捷径或替代方案|
| 1 |灵活性有限；主要路径的替代方案很少
| 2 |一些捷径；基本键盘支持，有限的批量操作|
| 3 |良好的加速器；键盘导航，一些定制|
| 4 |高度灵活；多路径、强大功能、可定制|

##### 8.美学和简约设计

界面不应包含不相关或很少需要的信息。每个元素都应该服务于一个目的。

**检查**：
- 每一步仅显示必要的信息
- 清晰的视觉层次引导注意力
- 有目的地使用颜色和强调
- 没有杂乱的装饰来争夺注意力
- 布局集中、整洁

**评分**：
|分数 |标准|
|-------|----------|
| 0 |压倒;一切都平等地争夺注意力|
| 1 |杂乱；噪音太大，很难找到重要的事情|
| 2 |有些杂乱；主要内容清晰，周边嘈杂|
| 3 |大部分是干净的；集中设计，视觉噪音小 |
| 4 |完美简约；每个元素都有其像素 |

##### 9. 帮助用户识别、诊断错误并从错误中恢复

错误消息应该使用简单的语言，准确地指出问题，并建设性地提出解决方案。

**检查**：
- 简单语言错误消息（用户没有错误代码）
- 具体问题识别（“电子邮件丢失@”而不是“输入无效”）
- 可行的恢复建议
- 在问题根源附近显示错误
- 非阻塞错误处理（不擦除表单）

**评分**：
|分数 |标准|
|-------|----------|
| 0 |隐秘错误；代码、行话或根本没有消息 |
| 1 |模糊错误；在没有指导的情况下“出了问题”|
| 2 |清晰但无益；指出了问题，但没有指出解决办法 |
| 3 |明确并提出建议；识别问题并提供后续步骤|
| 4 |完美康复；查明问题、建议修复、保留用户工作 |

##### 10.帮助和文档

即使系统无需文档即可使用，帮助也应该易于查找、以任务为中心且简洁。

**检查**：
- 可搜索的帮助或文档
- 上下文帮助（工具提示、内联提示、导游）
- 以任务为中心的组织（不是按功能组织）
- 简洁、可扫描的内容
- 无需离开当前上下文即可轻松访问

**评分**：
|分数 |标准|
|-------|----------|
| 0 |没有任何地方可以提供帮助 |
| 1 |存在帮助，但很难找到或不相关 |
| 2 |基本帮助；存在常见问题解答或文档，但与上下文无关 |
| 3 |良好的文档；可搜索，主要以任务为中心 |
| 4 |出色的上下文帮助；在正确的时刻提供正确的信息|

#### 问题严重性 (P0–P3)

用优先级标记评分过程中发现的每个问题：

|优先|名称 |描述 |行动|
|----------|------|-------------|--------|
| **P0** |封锁|完全阻止任务完成 |立即修复；这是一场精彩的比赛|
| **P1** |专业|造成重大困难或混乱 |发布前修复 |
| **P2** |次要|烦恼，但存在解决方法 |在下一次修复 |

### 基于角色的设计测试

通过 5 种不同用户原型的视角来测试界面。每个角色都暴露了不同的故障模式，而单一的“设计总监”视角会忽略这些模式。

**如何使用**：选择与被批评的界面最相关的 2-3 个角色。逐步了解每个角色的主要用户操作。报告具体的危险信号，而不是一般的问题。

---

#### 1. 不耐烦的高级用户：“Alex”

**简介**：同类产品专家。期望效率，讨厌手工。会寻找捷径或者离开。

**行为**：
- 跳过所有入门和说明
- 立即寻找键盘快捷键
- 尝试批量选择、批量编辑和自动化
- 因觉得不必要的必要步骤而感到沮丧
- 如果有任何事情感觉缓慢或居高临下，就放弃

**测试问题**：
- Alex 能在 60 秒内完成核心任务吗？
- 是否有常用操作的键盘快捷键？
- 可以完全跳过入职吗？
- 模态是否有键盘关闭（Esc）？
- 是否有“高级用户”路径（快捷方式、批量操作）？

**危险信号**（具体报告这些）：
- 强制教程或不可跳过的入门
- 主要操作没有键盘导航
- 无法跳过的缓慢动画
- 一次处理一个项目的工作流程，其中批次是自然的
- 低风险操作的冗余确认步骤

---

#### 2. 困惑的新手：“乔丹”

**简介**：从未使用过此类产品。每一步都需要指导。会放弃而不是弄清楚。

**行为**：
- 仔细阅读所有说明
- 在点击任何不熟悉的内容之前会犹豫
- 不断寻求帮助或支持
- 误解行话和缩写
- 采用任何标签最字面的解释

**测试问题**：
- 第一个动作在5秒内是否明显清晰？
- 所有图标都标有文字吗？
- 在决策点是否有上下文帮助？
- 术语是否假设有先验知识？
- 每一步是否都有明确的“后退”或“撤消”？

**危险信号**（具体报告这些）：
- 仅图标导航，没有标签
- 没有解释的技术术语
- 没有可见的帮助选项或指导
- 完成某项操作后后续步骤不明确
- 没有确认操作成功

---

#### 3. 依赖辅助功能的用户：“Sam”

**配置文件**：使用屏幕阅读器 (VoiceOver/NVDA)、仅键盘导航。可能存在视力低下、运动障碍或认知差异。

**行为**：
- 线性地浏览界面
- 依赖 ARIA 标签和标题结构
- 无法看到悬停状态或仅视觉指示器
- 需要足够的色彩对比度（最低 4.5:1）
- 可以使用浏览器缩放至 200%

**测试问题**：
- 整个主要流程可以仅通过键盘完成吗？
- 所有交互元素都可以通过可见的焦点指示器进行聚焦吗？
- 图像是否有有意义的替代文本？
- 颜色对比度是否符合 WCAG AA 标准（文本为 4.5:1）？
- 屏幕阅读器是否宣布状态更改（加载、成功、错误）？

**危险信号**（具体报告这些）：
- 仅点击交互，无需键盘替代
- 焦点指示器丢失或看不见
- 仅通过颜色传达的含义（红色 = 错误，绿色 = 成功）
- 未标记的表单字段或按钮
- 限时行动，无延期选项
- 破坏屏幕阅读器流程的自定义组件

---

#### 4. 故意压力测试仪：“Riley”

**个人资料**：有条不紊的用户，将界面推向幸福之路之外。测试边缘情况，尝试意外的输入，并探究体验中的差距。

**行为**：
- 有意测试边缘情况（空状态、长字符串、特殊字符）
- 提交包含意外数据的表单（表情符号、RTL 文本、非常长的值）
- 尝试通过向后导航、刷新中间流程或在多个选项卡中打开来破坏工作流程
- 查找 UI 承诺的内容与实际发生的情况之间的不一致
- 有条理地记录问题

**测试问题**：
- 边缘发生了什么（0 个项目、1000 个项目、很长的文本）？
- 错误状态是否正常恢复或使 UI 处于损坏状态？
- 工作流程中刷新时会发生什么？状态是否保留？
- 是否有一些功能看似有效，但结果却很糟糕？
- UI 如何处理意外输入（表情符号、特殊字符、从 Excel 粘贴）？

**危险信号**（具体报告这些）：
- 看似有效但默默失败或产生错误结果的功能
- 错误处理会暴露技术细节或使 UI 处于损坏状态
- 空状态，没有显示任何有用的信息（“没有结果”，没有指导）
- 刷新或导航时丢失用户数据的工作流程
- UI 不同部分中类似交互之间的行为不一致

#### 5. 分心的移动用户：“Casey”

**配置文件**：在旅途中单手使用手机。经常被打断。可能连接速度较慢。

**行为**：
- 仅使用拇指；更喜欢屏幕底部的操作
- 中途被中断并稍后返回
- 频繁地在应用程序之间切换
- 注意力有限且缺乏耐心
- 尽可能少地打字，更喜欢点击和选择

**测试问题**：
- 主要操作是否在拇指区域（屏幕的下半部分）？
- 如果用户离开并返回，状态是否保留？
- 它可以在慢速连接（3G）上工作吗？
- 表单可以使用自动完成和智能默认值吗？
- 触摸目标是否至少为 44×44pt？

**危险信号**（具体报告这些）：
- 重要操作位于屏幕顶部（拇指无法触及）
- 无状态持久性；选项卡切换或中断时进度丢失
- 需要大文本输入才能进行选择
- 每个页面都会加载大量资源（无延迟加载）
- 微小的点击目标或距离太近的目标

#### 项目特定角色

如果 `AGENTS.md` 包含 `## Design Context` 部分（由 `impeccable init` 生成），则从受众和品牌信息中派生 1-2 个附加角色：

1.阅读目标受众描述
2. 确定 5 个预定义角色未涵盖的主要用户原型
3. 按照此模板创建角色：

```
##### [Role]: "[Name]"

**Profile**: [2-3 key characteristics derived from Design Context]

**Behaviors**: [3-4 specific behaviors based on the described audience]

**Red Flags**: [3-4 things that would alienate this specific user type]
```

仅当真实的设计上下文数据可用时才生成特定于项目的角色。不要发明观众的详细信息；当不存在上下文时使用 5 个预定义角色。
