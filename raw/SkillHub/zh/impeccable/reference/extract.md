# 提取流程

识别可重用的模式、组件和设计标记，然后将它们提取并整合到设计系统中以进行系统重用。

## 第 1 步：发现设计系统

查找设计系统、组件库或共享 UI 目录。了解其结构：组件组织、命名约定、设计 token结构、导入/导出约定。

**关键**：如果不存在设计系统，请停止并使用 Codex 的结构化用户输入/问题工具（如果可用）；如果无法推断，请直接在聊天中询问以澄清您无法推断的内容。在创建之前。首先了解首选位置和结构。

## 第 2 步：识别模式

在目标区域寻找开采机会：

- **重复组件**：类似的 UI 模式使用 3 次以上（按钮、卡片、输入）
- **硬编码值**：应该是标记的颜色、间距、版式、阴影
- **不一致的变化**：同一概念的多种实现
- **组合模式**：重复的布局或交互模式（表单行、工具栏组、空状态）
- **字体样式**：重复的字体大小 + 粗细 + 行高组合
- **动画模式**：重复缓动、持续时间或关键帧组合

评估价值：仅提取出于相同目的使用过 3 次以上的事物。过早的抽象比重复更糟糕。

## 第三步：计划提取

制定系统的计划：

- **要提取的组件**：哪些 UI 元素成为可重用组件？
- **创建token**：哪些硬编码值成为设计 token？
- **支持的变体**：每个组件需要哪些变体？
- **命名约定**：与现有模式匹配的组件名称、token名称、props名称
- **迁移路径**：如何重构现有用途以使用新的共享版本

**重要**：设计系统逐渐增长。提取现在明显可重复使用的内容，而不是将来可能可重复使用的所有内容。

## 步骤 4：提取和丰富

构建改进的、可重用的版本：

- **组件**：清晰的 props API，具有合理的默认值、不同用例的适当变体、内置可访问性（ARIA、键盘导航、焦点管理）、文档和使用示例
- **设计 token**：清晰的命名（原始与语义）、正确的层次结构和组织、何时使用每个token的文档
- **模式**：何时使用此模式、代码示例、变体和组合

## 步骤 5：迁移

用新的共享版本替换现有的使用：

- **查找所有实例**：搜索您提取的模式
- **系统替换**：更新每次使用以消耗共享版本
- **彻底测试**：确保视觉和功能同等
- **删除死代码**：删除旧的实现

## 第 6 步：记录

更新设计系统文档：

- 将新组件添加到组件库中
- 记录token的使用和价值
- 添加示例和指南
- 更新任何故事书或组件目录

**从不**：
- 提取一次性的、特定于上下文的实现，而不进行泛化
- 创建的组件过于通用而毫无用处
- 不考虑现有设计系统约定的摘录
- 跳过正确的 TypeScript 类型或 prop 文档
- 为每个值创建标记（标记应具有语义含义）
- 提取意图不同的内容（两个看起来相似但用途不同的按钮应该分开）
