## 评估适应挑战

了解什么需要调整以及为什么：

1. **识别源上下文**：
   - 它最初的设计目的是什么？ （桌面网络？移动应用程序？）
   - 做了什么假设？ （大屏幕？鼠标输入？快速连接？）
   - 在当前环境下什么效果最好？

2. **了解目标上下文**：
   - **设备**：手机、平板电脑、台式机、电视、手表、打印？
   - **输入法**：触摸、鼠标、键盘、语音、游戏手柄？
   - **屏幕限制**：尺寸、分辨率、方向？
   - **连接**：快速 wifi、慢速 3G、离线？
   - **使用环境**：移动与桌面、快速浏览与专注阅读？
   - **用户期望**：用户对该平台有何期望？

3. **确定适应挑战**：
   - 什么不适合？ （内容、导航、功能）
   - 什么不起作用？ （触摸时的悬停状态，微小的触摸目标）
   - 有什么不合适的吗？ （移动端的桌面模式、桌面端的移动模式）

**关键**：适应是重新思考新环境的体验，而不是缩放像素。

## 规划适应策略

创建适合上下文的策略：

### 移动适配（桌面→移动）

**布局策略**：
- 单列而不是多列
- 垂直堆叠而不是并排堆叠
- 全宽组件而不是固定宽度
- 底部导航而不是顶部/侧面导航

**互动策略**：
- 触摸目标最小 44x44px（不依赖于悬停）
- 在适当的情况下滑动手势（列表、轮播）
- 底部表格而不是下拉菜单
- 拇指优先设计（拇指可触及的范围内进行控制）
- 更大的水龙头区域和更大的间距

**内容策略**：
- 渐进式披露（不要一次显示所有内容）
- 优先考虑主要内容（选项卡/手风琴中的次要内容）
- 较短的文字（更简洁）
- 更大的文本（最小 16 像素）

**导航策略**：
- 汉堡菜单或底部导航
- 降低导航复杂性
- 上下文粘性标题
- 导航流程中的后退按钮

### 平板电脑适配（混合方法）

**布局策略**：
- 两列布局（不是单列或三列）
- 次要内容的侧面板
- 主从视图（列表+详细信息）
- 基于方向的自适应（纵向与横向）

**互动策略**：
- 支持触摸和指针
- 触摸目标为 44x44px，但允许比手机更密集的布局
- 侧面导航抽屉
- 适当的多栏表格

### 桌面适配（移动端→桌面端）

**布局策略**：
- 多列布局（使用水平空间）
- 侧面导航始终可见
- 同时显示多个信息面板
- 具有最大宽度限制的固定宽度（不要拉伸到 4K）

**互动策略**：
- 将鼠标悬停在状态上以获取更多信息
- 键盘快捷键
- 右键单击上下文菜单
- 拖放有帮助的地方
- 使用 Shift/Cmd 进行多项选择

**内容策略**：
- 预先显示更多信息（渐进式披露较少）
- 具有多列的数据表
- 更丰富的可视化
- 更详细的描述

### 打印适应（屏幕→打印）

**布局策略**：
- 在逻辑点处分页
- 删除导航、页脚、交互元素
- 黑白（或有限颜色）
- 适当的装订边距

**内容策略**：
- 展开缩短的内容（显示完整的 URL、隐藏的部分）
- 添加页码、页眉、页脚
- 包括元数据（打印日期、页面标题）
- 将图表转换为适合打印的版本

### 电子邮件适应（网络 → 电子邮件）

**布局策略**：
- 窄宽度（最大 600 像素）
- 仅单列
- 内联 CSS（无外部样式表）
- 基于表格的布局（用于电子邮件客户端兼容性）

**互动策略**：
- 大而明显的 CTA（按钮而不是文本链接）
- 没有悬停状态（不可靠）
- 深层链接到网络应用程序以实现复杂的交互

## 实施调整

系统地应用更改：

### 响应断点

选择合适的断点：
- 手机：320px-767px
- 平板电脑：768px-1023px
- 桌面：1024px+
- 或内容驱动的断点（设计中断的地方）

### 布局适应技术

- **CSS Grid/Flexbox**：自动回流布局
- **容器查询**：基于容器而不是视口进行调整
- **`clamp()`**：流体尺寸介于最小和最大之间
- **媒体查询**：不同上下文的不同样式
- **显示属性**：显示/隐藏每个上下文的元素

### 触摸适应

- 增加触摸目标尺寸（最小 44x44 像素）
- 在交互元素之间添加更多间距
- 删除依赖悬停的交互
- 添加触摸反馈（波纹、亮点）
- 考虑拇指区域（到达底部比到达顶部更容易）

### 内容改编

- 谨慎使用 `display: none`（仍然下载）
- 渐进增强（核心内容优先，大屏幕增强）
- 屏幕外内容的延迟加载
- 响应式图像（`srcset`、`picture` 元素）

### 导航适配

- 将复杂的导航转换为移动设备上的汉堡/抽屉
- 移动应用程序的底部导航栏
- 桌面上的持久侧边导航
- 小屏幕上的面包屑以提供上下文

**重要**：在真实设备上进行测试。 DevTools 中的设备模拟很有帮助，但并不完美。

**从不**：
- 隐藏移动设备上的核心功能（如果重要，请使其发挥作用）
- 假设桌面 = 功能强大的设备（考虑可访问性、旧机器）
- 跨上下文使用不同的信息架构（令人困惑）
- 打破用户对平台的期望（移动用户期望移动模式）
- 忘记手机/平板电脑上的横向方向
- 盲目使用通用断点（使用内容驱动断点）
- 忽略桌面上的触摸（许多桌面设备都有触摸）

## 验证适配

跨上下文进行彻底测试：

- **真实设备**：在实际手机、平板电脑、台式机上测试
- **不同方向**：纵向和横向
- **不同的浏览器**：Safari、Chrome、Firefox、Edge
- **不同操作系统**：iOS、Android、Windows、macOS
- **不同的输入方式**：触摸、鼠标、键盘
- **边缘情况**：非常小的屏幕（320px），非常大的屏幕（4K）
- **连接速度慢**：在受限网络上进行测试

当适应感觉适合每个上下文时，将其移交给 `$impeccable polish` 进行最终传递。

## 参考资料

下面的部分以前是 `responsive-design.md`，现在是内联的，因此适应流程在一处拥有其深度响应参考。

### 响应式设计

#### 移动优先：正确编写

从移动设备的基本样式开始，使用 `min-width` 查询来分层复杂性。桌面优先 (`max-width`) 意味着移动设备首先加载不必要的样式。

#### 断点：内容驱动

不要追逐设备尺寸；让内容告诉你在哪里突破。开始缩小，拉伸直到设计破坏，在那里添加断点。三个断点通常就足够了（640、768、1024px）。对于没有断点的流体值，请使用 `clamp()`。

#### 检测输入法，而不仅仅是屏幕尺寸

**屏幕尺寸并不能告诉您输入方法。** 带触摸屏的笔记本电脑，带键盘的平板电脑。使用指针和悬停查询：

```css
/* Fine pointer (mouse, trackpad) */
@media (pointer: fine) {
  .button { padding: 8px 16px; }
}

/* Coarse pointer (touch, stylus) */
@media (pointer: coarse) {
  .button { padding: 12px 20px; }  /* Larger touch target */
}

/* Device supports hover */
@media (hover: hover) {
  .card:hover { transform: translateY(-2px); }
}

/* Device doesn't support hover (touch) */
@media (hover: none) {
  .card { /* No hover state - use active instead */ }
}
```

**关键**：不要依赖悬停来实现功能。触摸用户无法悬停。

#### 安全区域：处理缺口

现代手机有凹口、圆角和主页指示灯。使用`env()`：

```css
body {
  padding-top: env(safe-area-inset-top);
  padding-bottom: env(safe-area-inset-bottom);
  padding-left: env(safe-area-inset-left);
  padding-right: env(safe-area-inset-right);
}

/* With fallback */
.footer {
  padding-bottom: max(1rem, env(safe-area-inset-bottom));
}
```

**在元标记中启用 viewport-fit**：
```html
<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">
```

#### 响应式图像：正确处理

##### 带有宽度描述符的 srcset

```html
<img
  src="hero-800.jpg"
  srcset="
    hero-400.jpg 400w,
    hero-800.jpg 800w,
    hero-1200.jpg 1200w
  "
  sizes="(max-width: 768px) 100vw, 50vw"
  alt="Hero image"
>
```

**它是如何工作的**：
- `srcset` 列出可用图像及其实际宽度（`w` 描述符）
- `sizes` 告诉浏览器图像将显示多宽
- 浏览器根据视口宽度和设备像素比选择最佳文件

##### 艺术指导的图片元素

当您需要不同的裁剪/构图（不仅仅是分辨率）时：

```html
<picture>
  <source media="(min-width: 768px)" srcset="wide.jpg">
  <source media="(max-width: 767px)" srcset="tall.jpg">
  <img src="fallback.jpg" alt="...">
</picture>
```

#### 布局适应模式

**导航**：三个阶段：移动设备上的汉堡+抽屉、平板电脑上的水平紧凑、桌面上充满标签。 **表格**：使用 `display: block` 和 `data-label` 属性转换为移动设备上的卡片。 **渐进式披露**：对于可能在移动设备上折叠的内容，请使用 `<details>/<summary>`。

#### 测试：不要单独信任 DevTools

DevTools 设备模拟对于布局很有用，但会遗漏：

- 实际的触摸交互
- 真实的CPU/内存限制
- 网络延迟模式
- 字体渲染差异
- 浏览器镶边/键盘外观

**至少测试**：一台真正的 iPhone、一台真正的 Android、一台平板电脑（如果相关）。廉价的 Android 手机会暴露出在模拟器上永远不会出现的性能问题。

---

**避免**：桌面优先的设计。设备检测而不是特征检测。独立的移动/桌面代码库。忽略平板电脑和风景。假设所有移动设备都功能强大。
