# 工艺流程

构建具有无可挑剔的 UX 和 UI 质量的功能：塑造设计、确定视觉方向、构建真实的生产代码、检查和改进浏览器内，直到达到高端工作室标准。

在编写代码之前，您需要：加载 PRODUCT.md、识别寄存器并加载匹配的参考，以及此任务的确认设计方向（来自 `shape` 或由用户提供）。 PRODUCT.md 是项目上下文，而不是特定于任务的简介。

将任何批准的视觉方向（生成的模拟或规定的参考）视为构图、层次结构、密度、氛围、标志性主题和独特视觉动作的具体合同。不要让模拟取代结构、副本、可访问性或状态设计。但如果实际结果缺乏已批准方向的主要成分，那么实施就是错误的。

### Gates：不压缩

Craft 有**多个用户门**，而不是一个。当线束具有本机图像生成功能（Codex via `image_gen`）时，代码之前的门序列为：

1. **形状简介已确认**（第 1 步）
2. **回答方向问题**（codex.md 步骤 A）
3. **调色板已确认**（codex.md 步骤 B）
4. **批准或委托一个模拟方向**（codex.md 步骤 D）

你必须在每个门口停下来。 **单独的形状确认并不是开始编码的绿灯。** 这是开始 codex.md 步骤 A 的绿灯。压缩门 2 到 4，因为形状简报感觉已完成是此流程的主要故障模式。

当安全带缺乏本机图像生成时，门 2-4 会折叠到简报本身中，并且形状确认会直接进入代码。

## 步骤 0：项目基础

在形成之前，在编写代码之前：弄清楚您正在从事什么类型的项目。

查看工作目录。运行 `ls`。检查：

- 现有框架：`astro.config.mjs/ts`、`next.config.js/ts`、`nuxt.config.ts`、`svelte.config.js`、`vite.config.js/ts`、`package.json`（含框架 deps）、`Cargo.toml` + Leptos/Yew， `Gemfile` + 导轨。 **如果找到，请使用它。** 不要启动并行构建，不要引入第二个框架，不要直接写入 `dist/` 或 `build/`。无论项目有什么管道，都要尊重它。
- 现有组件库或设计系统：`src/components/`、`app/components/`、`tokens.css` / `theme.ts`、`astro.config` `integrations`。在添加之前先阅读其中的内容。
- 现有图标集：`lucide-react`、`@phosphor-icons/react`、`@iconify/*`、`assets/icons/` 中的手卷 SVG 精灵。 **使用项目中已有的**；不要引入第二组。

如果目录是空的（未开发的），不要默默地选择框架。通过 AskUserQuestion 工具询问用户，并在摘要中给出合理的默认值：

```text
What should this be built on?
  - Astro (default for content-led brand sites, landing pages, marketing surfaces)
  - SvelteKit / Next.js / Nuxt (when the brief implies an app surface or significant interactivity)
  - Single index.html (one-shot demo, prototype, or a deliberately framework-free experiment)
```

默认值：Astro 用于品牌简介，该项目现有的产品简介框架。问一次；不要在任务中再次询问。

## 第 1 步：塑造设计

运行 $impeccable shape，传递用户提供的任何功能描述。形状对于工艺品来说是**必需的**；它产生了确定的方向。

显示形状输出并停止。在编写代码之前等待用户确认、覆盖或纠正过程。

如果用户已经单独提供了确认的内裤或跑步形状，请使用它并跳过此步骤。

当原始提示 + PRODUCT.md 已经回答了范围、内容和视觉方向而没有真正的歧义时，形状输出可以是**紧凑**（3-5 个项目符号说明您正在构建的内容和视觉通道，以一两个特定问题或“确认或覆盖”结束）。完整的 10 部分结构化概要是为真正模糊、多屏幕或利益相关者繁重的任务而保留的。不要为了显得完整而在长篇文章中塞入清晰的摘要；同样，不要为了看起来高效而跳过暂停。

如果线束具有本机图像生成功能 (Codex)，则紧凑形状的“确认或覆盖”将前进到 **步骤 3 和 codex.md 流程**，而不是步骤 4。相应地表述结束语：“确认或覆盖；一旦我们锁定方向，我将在生成任何模拟之前运行几个调色板和参考问题。”这会阻止模型将形状确认读取为绿色代码。

## 步骤 2：加载参考文献

根据设计概要的“推荐参考”部分，查阅相关的无可挑剔的参考文件。至少，请始终咨询：

- [layout.md](layout.md) 用于布局、间距、网格、容器查询、光学调整
- [typeset.md](typeset.md) 用于类型层次结构、字体选择、Web 字体加载、OpenType 功能（参考资料部分）

然后根据简报的需要添加参考文献：
- 复杂的交互或形式？咨询[interaction-design.md](interaction-design.md)
- 动画或过渡？查阅[animate.md](animate.md)（参考资料涵盖运动材质、持续时间、缓动、感知性能）
- 色彩浓重还是主题鲜明？查阅[colorize.md](colorize.md)（参考资料涵盖OKLCH、调色板结构、深色模式、对比度）
- 响应要求？查阅[adapt.md](adapt.md)（参考资料涵盖断点、输入法、安全区域、响应图像）
- 大量的副本、标签或错误？查阅[clarify.md](clarify.md)（参考资料涵盖按钮标签、错误公式、语音/语气、翻译）

## 步骤 3：视觉方向和资产（Harness-Gated）

如果线束具有**本机图像生成**（当前通过 `image_gen` 进行 Codex），则此步骤是强制性的。 **停止并加载 [codex.md](codex.md)**。它涵盖调色板生成、模拟探索、批准循环、模拟保真库存以及通过 `impeccable_asset_producer` 子代理进行的资产切片。按照该文件中的步骤 A-F 进行操作，然后返回此处执行步骤 4。

如果线束缺乏本机图像生成，**在一行中说明由于线束缺乏本机图像生成而跳过视觉方向生成步骤，然后继续**。需单行公告；它迫使人们做出有意识的决定，而不是让这一步悄然消失。简介是您唯一的视觉参考。直接从中实施，将任何命名的锚参考和简报的“设计方向”视为合同。

无论您是否生成模拟：不要用通用卡片、项目符号、表情符号、虚假指标、装饰性 CSS 面板或填充副本替换所需的图像。以图像为主导的简报（餐厅、酒店、杂志、摄影、爱好者社区、食品、旅行、时尚、产品）在构建中需要真实或来源的图像，而不是 CSS 风景。

## 步骤 4：达到生产质量

**先决条件。** 如果步骤 3 将您引导至 codex.md（可用本机图像生成），则该文件中的步骤 A 到 D 必须在任何代码之前完成：回答问题、确认调色板、生成模拟、批准或委派一个方向。 **在完成之前不要提及实施、文件路径或补丁计划。** 确认的形状概要是不够的；还需要注意。压缩这些门的模型是已经失败的模型。

按照设计概要实现该功能。构建通道，以便结构、视觉系统、状态、运动/媒体和响应行为都得到刻意的关注。下面的列表是完成的定义，而不是灵感。

### 生产栏

- **真实内容。** 演示时没有占位符副本、占位符图像、无效链接、虚假控件或未使用的脚手架。
- **保留批准的模拟的主要成分。** 缺少的英雄对象、世界/产品图像、部分结构、CTA/导航处理或独特的图案都是阻塞缺陷，除非用户接受更改。
- **语义第一。** 真实标题、地标、标签、表单关联、按钮/链接语义、可访问名称、需要时的状态公告。
- **故意的间距和对齐。** 无默认间隙、任意边距、不平衡的空白或意外的光学未对齐。
- **有意的排版。** 选择加载策略，清晰的层次结构，可读的度量，稳定的换行符，在任何宽度下都不会溢出。
- **真实的状态覆盖。** 默认、悬停、焦点可见、活动、禁用、加载、错误、成功、空、溢出、长/短文本、首次运行。
- **完成的交互质量。**键盘路径、触摸目标、反馈计时、滚动行为、状态转换、无仅悬停功能。
- **连贯的图标集。** 使用项目既定的集；否则选择一个库或使用可访问的文本。不要混合。
- **尊重构建管道。** 编辑源文件并运行项目的构建（`npm run build` 或同等版本）。不要使用 `cat`、heredoc 或 Bash 重定向写入 `build/` / `dist/` / `.next/`；它会跳过资产哈希、图像优化、代码分割和 CSS 提取，并生成开发服务器无法提供的输出。
- **在引用图像 URL 之前验证它们。** 使用图像搜索 MCP 或 web-fetch（如果可用）；猜测照片 ID 会作为损坏的图像占位符发送。如果没有验证，请选择较少的您有信心的图像。
- **优化的图像和媒体。** 正确的尺寸、有用的替代文本、折叠下方的延迟加载、实用时的现代格式、用于光栅的响应式 `srcset`/`picture`、工作区之外没有留下任何项目引用的资源。
- **高级运动。** 使用大气模糊、滤镜、遮罩、阴影、显示来改善体验。避免随意的布局属性动画，绑定昂贵的效果，验证浏览器中的平滑度，尊重减少的运动，并避免阻碍任务完成的编排。
- **可维护。** 可重用的本地模式、清晰的组件边界、项目约定。当本地模式存在时，没有光栅化的 UI 文本或一次性黑客攻击。
- **技术上干净。** 生产构建过程，没有控制台错误，没有可避免的布局变化，没有不必要的依赖关系，没有损坏的资产路径。
- **不确定时询问。** 如果发现实质性改变了概要或批准的方向，请停下来询问。别猜了。

## 步骤 5：可视化迭代

像设计师一样看看你建造的东西。您的眼睛就是安全带为您提供的任何东西：连接的浏览器、屏幕截图工具、剧作家或询问用户。使用它们进行响应式测试（至少是移动设备、平板电脑、桌面设备）和一般视觉验证。

如果您的工具返回文件路径，请将 PNG 读回到对话中。您未阅读的屏幕截图不算数。

对于长形品牌表面，请单独检查主要部分。缩略图隐藏了间距、剪切和级联缺陷。

第一次通过后，针对简报、批准的模拟的主要成分（英雄轮廓、主题、图像、导航/CTA、密度）以及无可挑剔的“禁忌”写出诚实的评论。修补材料缺陷并重新检查。 **不要发明缺陷来证明迭代。** 自信的“第一次清理，交付”胜过虚假修复。

主动检查：响应行为（组合，而不是收缩）、每种状态（空/错误/加载/边缘）、工艺细节（间距、对齐、层次结构、对比度、运动计时、焦点）、性能基础知识。退出栏：在高端工作室评论中是站得住脚的。

检测器或 QA 输出仅是缺陷证据；从不证明工作已经完成。

## 第 6 步：展示

将结果呈现给用户：
- 显示该功能的主要状态
- 总结检查的浏览器/视口以及检查后所做的最重要的修复
- 遍历关键状态（空、错误、响应）
- 解释与设计概要相关的设计决策，以及在使用时与所选的北极星模型相关的设计决策。包括任何可接受的与模拟的偏差；不要隐藏未实现的模拟成分。
- 诚实地记下任何剩余的限制或后续风险
- 问：“什么有效？什么无效？”
