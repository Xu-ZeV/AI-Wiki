> **需要额外的背景**：质量栏（MVP 与旗舰）。

进行一丝不苟的最后一次检查，捕捉所有区分好工作和伟大工作的小细节。出厂和抛光的区别。

检测器和自动 QA 输出仅是缺陷证据。干净的脚本结果永远不能证明设计是强大的；收集浏览器证据并检查真实的交互路径。

## 设计系统发现

将功能与设计系统保持一致是**不是可选的**。没有对齐的抛光是漂移之上的装饰，它会让下一个人的工作变得更加困难。发现先于任何其他抛光工作。

1. **查找设计系统**：搜索设计系统文档、组件库、样式指南或token定义。研究核心模式：设计原则、目标受众、颜色标记、间距比例、排版样式、组件 API、动作约定。
2. **注意约定**：共享组件如何导入？使用什么间距比例？哪些颜色来自标记，哪些颜色来自硬编码值？建立了哪些运动和交互模式？哪些流形状用于可比较的操作（模态与全页、内联与路由、模糊保存与显式提交）？
3. **识别偏差，然后命名根本原因**：对于每个偏差，将其分类为**缺失标记**（该值应该存在于系统中，但实际上并不存在）、**一次性实现**（共享组件已存在但未使用）或**概念错位**（功能的流程、IA 或层次结构与相邻功能不匹配）。修复方法因类别而异：修补值、交换到共享组件或重新设计流程。解决症状而不指出原因是漂移的复合方式。

如果存在设计系统，则抛光**必须**将功能与其对齐。如果不存在，请根据代码库中可见的约定进行完善。 **如果有关系统的任何内容不明确，请询问。永远不要猜测设计系统原理。**

## 抛光前评估

在接触任何事情之前先了解当前的状态和目标：

1. **审核完整性**：
   - 功能完整吗？
   - 是否有需要保留的已知问题（用 TODO 标记）？
   - 质量标准是多少？ （MVP 与旗舰功能？）
   - 什么时候发货？ （打磨需要多长时间？）

2. **考虑体验第一**：谁实际使用这个，对他们来说最好的体验是什么？有效的设计胜过装饰性的修饰；一个看起来很漂亮但是却与用户流量相冲突的功能并没有经过打磨。在打开 DevTools 之前，从他们的角度出发。

3. **确定抛光区域**：
   - 视觉不一致
   - 间距和对齐问题
   - 交互状态差距
   - 复制不一致
- 边缘情况和错误状态
   - 加载和过渡平滑度
   - 信息架构和流程漂移（此功能是否像相邻功能那样揭示复杂性？）

4. **引入任何先前的批评**（可选信号）：如果 `$impeccable critique` 已在同一目标上运行，则其优先级问题对于首先要解决的问题是有用的。将目标解析为文件路径或 URL，然后：
   ```bash
   slug=$(node .agents/skills/impeccable/scripts/critique-storage.mjs slug "<resolved>")
   node .agents/skills/impeccable/scripts/critique-storage.mjs latest "$slug"
   ```
   退出 0，body = 找到；将 P0/P1 项目折叠到您的抛光列表中并提及快照路径，以便用户看到您所阅读的内容。退出 2 = 无快照，不带快照继续。批评只是众多意见之一。无论哪种方式，都请自行通行证。

5. **分类装饰性与功能性**：将每个问题分类为**装饰性**（看起来不美观，不会妨碍用户）或**功能性**（破坏、阻碍或混淆体验）。当打磨时间紧迫时，首先考虑功能问题；化妆品可以在后续中落地。质量应一致；永远不要让一个角落变得完美而让另一个角落变得粗糙。

**关键**：抛光是最后一步，而不是第一步。不要打磨功能不完整的工作。

## 系统地打磨

有条不紊地处理这些维度：

### 视觉对齐和间距

- **像素完美对齐**：一切都对齐网格
- **一致的间距**：所有间隙均使用间距比例（无随机 13px 间隙）
- **光学对齐**：调整视觉重量（图标可能需要偏移以实现光学居中）
- **响应一致性**：所有断点处的间距和对齐工作
- **网格粘附**：元素捕捉到基线网格

**检查**：
- 启用网格覆盖并验证对齐
- 使用浏览器检查器检查间距
- 在多个视口尺寸下进行测试
- 寻找“感觉”不对劲的元素

### 信息架构和流程

对畸形流程进行视觉修饰是浪费精力。将体验的“形状”与系统相匹配，而不仅仅是表面。

- **渐进式披露**：与相邻特征相比，匹配何时披露的数量。设置页面显示 40 个字段，而应用程序的其余部分一次显示 5 个字段，这是一种偏差，即使每个字段的样式都很完美。
- **已建立的用户流程**：多步骤操作遵循与其他地方的类似流程相同的形状：模态与全页、内联编辑与单独路径、模糊保存与显式提交、乐观与悲观更新。
- **层次结构和复杂性**：相同的概念权重始终具有相同的视觉权重。主要操作不会在产品的某个角落变成第三级操作，第三级操作也不会大喊大叫。
- **清空、加载和到达转换**：内容的到达、更新和离开方式与其在相邻功能中的表现相匹配。
- **命名和心理模型**：该功能使用与系统其他部分相同的名词和动词。这里的“工作区”不应该是三个屏幕之外的“项目”。

### 版式细化

- **层次结构一致性**：相同的元素始终使用相同的尺寸/重量
- **行长**：正文 45-75 个字符
- **行高**：适合字体大小和上下文
- **寡妇和孤儿**：最后一行没有任何单词
- **连字**：适合语言和列宽
- **字距调整**：根据需要调整字母间距（尤其是标题）
- **字体加载**：无 FOUT/FOIT 闪烁

### 颜色和对比度

- **对比度**：所有文本均符合 WCAG 标准
- **一致的token使用**：没有硬编码颜色，全部使用设计 token
- **主题一致性**：适用于所有主题变体
- **颜色含义**：相同的颜色始终表示相同的事物
- **可对焦**：对焦指示器可见且具有足够的对比度
- **颜色为灰色**：切勿将灰色文本放在彩色背景上；使用该颜色或透明度的阴影

### 交互状态

每个交互元素都需要所有状态：

- **默认**：休息状态
- **悬停**：微妙的反馈（颜色、比例、阴影）
- **焦点**：键盘焦点指示器（切勿移除而不更换）
- **主动**：点击/点击反馈
- **禁用**：显然是非交互式的
- **加载**：异步操作反馈
- **错误**：验证或错误状态
- **成功**：成功完成

**缺失的状态会造成混乱和破碎的体验**。

### 微交互和过渡

- **平滑过渡**：所有状态变化都适当地动画化（150-300ms）
- **一致的缓动**：使用 escape-out-quart/quint/expo 进行自然减速。绝不弹跳或有弹性；他们感觉过时了。
- **无卡顿**：流畅的动画；在添加抛光时使用大气模糊/滤镜/遮罩/阴影效果，但会限制昂贵的绘画区域并避免随意的布局属性动画
- **适当的动作**：动作是为了目的，而不是装饰
- **减少运动**：尊重 `prefers-reduced-motion`

### 内容和副本

- **一致的术语**：相同的事物始终称为相同的名称
- **一致的大写**：标题大小写与句子大小写一致应用
- **语法和拼写**：没有拼写错误
- **适当的长度**：不要太罗嗦，也不要太简洁
- **标点符号一致性**：句子上的句号，而不是标签上的句号（除非所有标签都有句号）

### 图标和图像

- **一致的风格**：来自同一系列或匹配风格的所有图标
- **适当的尺寸**：图标尺寸与上下文一致
- **正确对齐**：图标与相邻文本光学对齐
- **替代文本**：所有图像都有描述性替代文本
- **加载状态**：图像不会导致布局移位，宽高比正确
- **Retina 支持**：高 DPI 屏幕的 2 倍资源

### 表格和输入

- **标签一致性**：所有输入均正确标记
- **所需指标**：清晰一致
- **错误消息**：有用且一致
- **Tab 键顺序**：逻辑键盘导航
- **自动对焦**：适当（不要过度使用）
- **验证时间**：一致（模糊与提交）

### 边缘情况和错误状态

- **加载状态**：所有异步操作都有加载反馈
- **空状态**：有用的空状态，而不仅仅是空白
- **错误状态**：清除错误消息和恢复路径
- **成功状态**：确认成功操作
- **长内容**：处理很长的名称、描述等。
- **无内容**：优雅地处理丢失的数据
- **离线**：适当的离线处理（如果适用）

### 响应能力

- **所有断点**：测试手机、平板电脑、桌面
- **触摸目标**：触摸设备上最小为 44x44px
- **可读文本**：移动设备上的文本不得小于 14 像素
- **无水平滚动**：内容适合视口
- **适当的重排**：内容按逻辑进行调整

### 性能

- **快速初始加载**：优化关键路径
- **无布局移位**：元素在加载后不会跳转（CLS）
- **流畅的交互**：无滞后或卡顿
- **优化图像**：适当的格式和尺寸
- **延迟加载**：屏幕外内容延迟加载

### 代码质量

- **删除控制台日志**：生产中没有调试日志记录
- **删除注释代码**：清理死代码
- **删除未使用的导入**：清理未使用的依赖项
- **一致的命名**：变量和函数遵循约定
- **类型安全**：没有 TypeScript `any` 或忽略错误
- **辅助功能**：正确的 ARIA 标签和语义 HTML

## 最终验证

在标记为完成之前：

- **自己使用**：实际与该功能交互。
- **在真实设备上测试**：不仅仅是浏览器开发工具。
- **请其他人评论**：新鲜的眼睛捕捉事物。
- **与设计比较**：匹配预期设计。
- **检查所有状态**：不要只测试快乐路径。
- **谨慎对待自动化**：在可用且相关时运行检测器或 QA 命令，修复其缺陷，但切勿引用干净的结果作为工作已完成的证据。

## 清理

打磨后，保证代码质量：

- **替换自定义实现**：如果设计系统提供您重新实现的组件，请切换到共享版本。
- **删除孤立代码**：删除未使用的样式、组件或因修改而过时的文件。
- **合并token**：如果您引入了新值，请检查它们是否应该是token。
- **验证干燥度**：寻找抛光和巩固过程中引入的重复。
