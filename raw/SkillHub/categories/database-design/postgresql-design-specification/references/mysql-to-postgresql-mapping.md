# 上游 MySQL 设计规范 → PostgreSQL 逐条映射

来源：`Highflyer/MySQL-Design-Specification`，commit `14f78853e8b601b78ce2abfc0120b4cf55e06e37`，原文仅 1 个 `README.md`（109 条编号条款：【高危】2 + 【强制】54 + 【建议】53）。

下表逐条对应 109 条条款，共 109 行映射行；级别沿用上游标注。表格之外另有 4 行条款冲突裁决。

| 上游条款号 | 级别 | MySQL 要点 | PostgreSQL 14+ 做法 |
| --- | --- | --- | --- |
| [2.1.1-1] | 强制 | 要求标识符全小写 | 同上游：PG 未加引号的标识符会折叠为小写，统一小写 |
| [2.1.1-2] | 强制 | 名称不含空格，用下划线连接 | 同上游：PG 中含空格的名称必须加引号，禁止 |
| [2.1.1-3] | 强制 | 名称只用英文字母，不含数字 | 同上游 |
| [2.1.1-4] | 强制 | 名称有效、可理解 | 同上游 |
| [2.1.1-5] | 强制 | 名称自解释 | 同上游 |
| [2.1.1-6] | 强制 | 名称不超过 32 个字符 | 同上游：PG 标识符硬上限 63 字节，超长静默截断，32 字符更安全 |
| [2.1.1-7] | 强制 | 避免使用前缀 | 同上游 |
| [2.1.2-1] | 强制 | 库名遵守全部一般命名规则 | 同上游 |
| [2.1.2-2] | 强制 | 库名使用单数 | 同上游 |
| [2.1.2-4] | 强制 | 库名格式 业务系统名_子系统名 | PG 对应 database 与 schema 两级：单库多子系统时用 schema 承载子系统名 |
| [2.1.2-5] | 强制 | 分库命名 库通配名_编号 或 库通配名_时间 | 分片命名沿用同一约定，编号从 0 递增 |
| [2.1.2-6] | 强制 | 建库显式指定字符集，且只能是 utf8/utf8mb4 | 改为 CREATE DATABASE ... ENCODING 'UTF8' LC_COLLATE/LC_CTYPE；PG 的 UTF8 无 3 字节限制，无需 utf8mb4；encoding/collation 创建后基本不可变更 |
| [2.1.3-1] | 强制 | 表名遵守全部一般命名规则 | 同上游 |
| [2.1.3-2] | 强制 | 表名使用单数 | 同上游 |
| [2.1.3-3] | 强制 | 相关模块表名体现 join 关系（user / user_login） | 同上游 |
| [2.1.3-4] | 强制 | 建表显式指定字符集 utf8/utf8mb4 | 不适用：PG 编码与排序规则继承自 database，无需逐表声明，仅在特殊排序需求时写列级 COLLATE |
| [2.1.3-5] | 强制 | 建表显式指定存储引擎，一律用 InnoDB | 不适用：PG 无存储引擎概念，统一堆表 + MVCC + TOAST，物理隔离用 tablespace 或声明式分区 |
| [2.1.3-6] | 强制 | 建表必须有 comment | PG 用 COMMENT ON TABLE / COMMENT ON COLUMN |
| [2.1.3-7] | 强制 | 主键 id int/bigint auto_increment；业务标识列不设主键，另建 unique key | PG 用 bigint GENERATED BY DEFAULT AS IDENTITY（≥10）；业务键建 UNIQUE 约束；上游的 page 分裂理由对应 PG 的独立索引 + ctid 存放模型 |
| [2.1.3-8] | 建议 | 核心表必须有 create_time / update_time | 同上游：类型用 timestamptz，DEFAULT now() |
| [2.1.3-9] | 建议 | 所有字段 NOT NULL，按需定义 DEFAULT | 同上游：PG 中 NULL 仅行尾不占位，但聚合偏差与迁移歧义风险一致 |
| [2.1.3-10] | 建议 | blob/text 大字段垂直拆分，按需 select | 同上游：PG 的 TOAST 自动行外存储，但随行读取仍有 I/O 开销 |
| [2.1.3-11] | 建议 | 反范式设计，冗余常用 join 字段 | 同上游 |
| [2.1.3-12] | 强制 | 中间表 tmp_ 前缀、备份表 bak_ 前缀，定期清理 | 同上游：PG 补充 TEMPORARY/UNLOGGED 表与物化视图 |
| [2.1.3-13] | 强制 | 超过 100W 行的大表 alter table 需审核并低峰执行 | 同上游：PG 优先不重写变更。加列仅带非易失（non-volatile）默认值才自 PG 11 起不重写表（易失默认值、生成列、identity 列、带约束 domain 仍重写）；配合 CREATE INDEX CONCURRENTLY 与 NOT VALID + VALIDATE CONSTRAINT（NOT VALID 9.1 起用于外键、9.2 起用于 CHECK） |
| [2.1.4-1] | 强制 | 字段名遵守全部一般命名规则 | 同上游 |
| [2.1.4-2] | 建议 | 字段名尽量短，一到两个单词 | 同上游 |
| [2.1.4-3] | 强制 | 避免保留字作字段名（order/date/name），加前缀区分 | 同上游：PG 保留字集合不同，用 pg_get_keywords() 自查 |
| [2.1.4-4] | 强制 | 字段名不得与表名相同 | 同上游 |
| [2.1.4-5] | 强制 | 在数据库模式上定义外键 | 同上游：PG 默认启用声明式外键（与 [2.2.5-3] 的冲突见下方裁决 3） |
| [2.1.4-6] | 强制 | 避免缩写或首字母缩写词 | 同上游 |
| [2.1.4-7] | 强制 | 外键列必须带表名语义，如 blog_id | 同上游 |
| [2.1.5-1] | 建议 | 自增列推荐 bigint，避免 int 溢出 | PG 用 bigint + GENERATED BY DEFAULT AS IDENTITY，无表级自增锁竞争 |
| [2.1.5-2] | 建议 | 低选择性状态/类型字段用 tinyint 或 smallint | PG 用 smallint（无 tinyint 类型） |
| [2.1.5-3] | 建议 | IP 用 int，配 inet_aton/inet_ntoa 与应用层 ip2long | PG 用原生 inet 类型，可直接比较、建索引并支持网段运算，无需转换函数 |
| [2.1.5-4] | 建议 | 不推荐 enum/set（浪费空间、变更不便）；异议建议 enum + 严格模式 | 见下方裁决 1：优先 text + CHECK，或原生 enum（ALTER TYPE ... ADD VALUE 可用但删改困难），量大时 smallint + 应用层字典 |
| [2.1.5-5] | 建议 | 不推荐 blob/text，InnoDB 行溢出让 overflow-page 被加载 | 不适用（改写）：PG 中 text 与 varchar(n) 无性能差异，超阈值 TOAST 行外存储，二进制用 bytea |
| [2.1.5-6] | 建议 | 金额用 int 存「分」，不建议 decimal（二进制编码、效率低） | 不适用：PG 的 numeric 是精确十进制，无精度损失，推荐 numeric(p,s)；仅应用层明确要求分单位时用 bigint |
| [2.1.5-7] | 建议 | 文本用 varchar，字符数不超过 2700；给出 65535 字节行上限与 mediumtext/longtext 分级 | 不适用（改写）：PG 无该行文本上限与文本类型分级，统一建议 text，长度约束用 CHECK (length(col) <= n) 表达 |
| [2.1.5-8] | 建议 | 时间优先 timestamp（4 字节），或用 int + unix_timestamp()/from_unixtime() | 改写：PG 统一 timestamptz，不用整数存时间，需要 epoch 时用 extract(epoch from ...) / to_timestamp() |
| [2.1.6-1] | 强制 | InnoDB 表必须 id int/bigint auto_increment 主键，主键值禁止更新 | 同上游：主键 id bigint + GENERATED BY DEFAULT AS IDENTITY，主键值禁止更新 |
| [2.1.6-2] | 建议 | 主键 pk_、唯一键 uk_、普通索引 idx_ 前缀，全小写 | 同上游 |
| [2.1.6-3] | 强制 | 索引类型必须 BTREE（MEMORY 表可用 HASH） | 改写：PG 默认 btree，另有 gin/gist/brin/hash（hash 仅等值比较）按场景选型，并支持 INCLUDE 覆盖索引（PG 11 起） |
| [2.1.6-4] | 强制 | 单个索引记录长度不超过 64KB | 改写：PG btree 索引项不得超过页的约 1/3（官方口径 approximately one-third of a page），超长值改用表达式索引或 substr 前缀索引；hash 仅等值比较，不能解决长度问题 |
| [2.1.6-5] | 建议 | 单表索引建议不超过 5 个（上游注：MySQL 本身无个数限制） | 同上游：PG 每个索引都要维护 WAL 与 VACUUM，写入放大是主要成本 |
| [2.1.6-6] | 建议 | 优先联合索引，区分度高的字段在前 | 同上游 |
| [2.1.6-7] | 建议 | 多表 join 时保证被驱动表连接列有索引 | 同上游 |
| [2.1.6-8] | 建议 | 避免冗余索引：有 key(a,b) 时 key(a) 冗余 | 同上游：PG 还需注意重复前缀 btree 索引与完全相同的表达式索引 |
| [2.1.6-9] | 建议 | 选择性超过 20% 时全表扫描更优，可不建索引 | 同上游：PG 以 EXPLAIN (ANALYZE, BUFFERS) 实测，可改 brin 或 partial index（部分索引）并保持统计信息 |
| [2.1.7-1] | 强制 | 分区键必须有索引或为组合索引首列 | 同上游 |
| [2.1.7-2] | 强制 | 单个分区表的分区数不能超过 1024 | 改写：沿用上游 1024 作为运维上限；分区数越多规划/加锁开销越大，经验值数百以内并需实测；受官方 Limitations 约束（唯一约束/主键须含全部分区键） |
| [2.1.7-3] | 强制 | 上线前必须指定分区创建与清理策略 | 同上游：PG 常用 DETACH PARTITION + 归档表，避免大范围 DELETE |
| [2.1.7-4] | 强制 | 访问分区表的 SQL 必须包含分区键 | 同上游：PG 借此触发分区裁剪 |
| [2.1.7-5] | 建议 | 单分区不超过 2G、总大小不超过 50G、总分区数不超过 20 | 同上游：PG 用 pg_relation_size / pg_total_relation_size 度量 |
| [2.1.7-6] | 强制 | 分区表 alter table 必须在业务低峰期执行 | 同上游 |
| [2.1.7-7] | 强制 | 分库策略下库的数量不超过 1024 | 同上游 |
| [2.1.7-8] | 强制 | 分表策略下表的数量不超过 4096 | 同上游 |
| [2.1.7-9] | 建议 | 单分表不超过 500W 行，ibd 文件不超过 2G | 改写：PG 无 ibd 文件概念，改用 pg_total_relation_size() 观察表与索引总大小 |
| [2.1.7-10] | 建议 | 水平分表用取模，日志/报表类按日期分表 | 同上游：PG 优先声明式分区（RANGE 按时间、HASH 取模、LIST 枚举维度） |
| [2.1.8-1] | 强制 | 库、表、列字符集必须一致，为 utf8 或 utf8mb4 | 改写：PG 统一 UTF8，列级 collation 保持一致，避免混用导致索引失效 |
| [2.1.8-2] | 强制 | 前端程序字符集与库表一致，统一 utf8 | PG 落地：客户端连接显式 client_encoding = 'UTF8' |
| [2.1.9-1] | 建议 | 不用 model，手写 SQL + 绑定变量 | 同上游：PG 绑定变量即扩展查询协议参数，可复用执行计划 |
| [2.1.9-2] | 建议 | 连接必须有超时与失败重连，重试留间隔 | 同上游：PG 侧配合 idle_in_transaction_session_timeout |
| [2.1.9-3] | 建议 | 报错尽量透出数据库原生错误信息 | 同上游 |
| [2.1.9-4] | 建议 | 连接池需配置初始/最小/最大连接数、超时与回收 | 同上游：PG 每连接一个进程，max_connections 有限，超配会耗尽连接 |
| [2.1.9-5] | 建议 | log/history 表上线前必须有清理或归档方案 | 同上游：PG 可用分区 + DETACH 归档，避免大范围 DELETE 造成表膨胀 |
| [2.1.9-6] | 建议 | 考虑主从延迟，强一致读走主库 | 同上游：PG 为流复制备库读，强一致读回主库或走只读路由判断 |
| [2.1.9-7] | 建议 | 并发更新尽量基于主键，减少行锁范围 | 同上游 |
| [2.1.9-8] | 建议 | 业务逻辑加锁顺序保持一致，避免死锁 | 同上游 |
| [2.1.9-9] | 建议 | 读写比大于 10:1 的热点行/列放缓存 | 同上游 |
| [2.2.1-1] | 强制 | select 必须写具体字段，禁止 select * | 同上游 |
| [2.2.1-2] | 强制 | insert 必须指定具体字段名 | 同上游 |
| [2.2.1-3] | 建议 | 批量 insert 值不超过 5000 个，过多会引起主从同步延迟 | 同上游：PG 更大批量优先用 COPY 或 unnest 展开 |
| [2.2.1-4] | 建议 | 不用 union，推荐 union all，子句不超过 5 个 | 同上游：去重有额外排序与哈希开销 |
| [2.2.1-5] | 建议 | in 值列表限制在 500 以内 | 同上游 |
| [2.2.1-6] | 建议 | 事务里批量更新控制数量并 sleep，少量多次 | 同上游 |
| [2.2.1-7] | 强制 | 事务涉及的表必须全部是 InnoDB 表，否则不会全部回滚 | 不适用：PG 无存储引擎概念，也不支持跨 database 事务，等价为「一个事务只访问同一 database 内的对象」，跨库须用 FDW/两阶段提交并评审 |
| [2.2.1-8] | 强制 | 写入与事务发主库，只读 SQL 发从库 | 同上游：PG 落到主库写、hot standby 读，并注意 synchronous_commit 与只读副本路由 |
| [2.2.1-9] | 强制 | 除 100 行以内静态小表，DML 必须有 where 且走索引 | 同上游 |
| [2.2.1-10] | 强制 | 生产禁用 hint，如 sql_no_cache、force index、ignore key、straight join | 改写：PG 无 hint 语法且这些关键字不存在，必要时用 pg_hint_plan 扩展或改写 SQL，并写明理由 |
| [2.2.1-11] | 强制 | where 等号左右字段类型必须一致 | 同上游：PG 类型不一致会触发隐式转换、可能不命中索引 |
| [2.2.1-12] | 建议 | select/update/delete/replace 要有 where 且走索引 | 同上游（PG 无 replace 语句，upsert 用 ON CONFLICT） |
| [2.2.1-13] | 强制 | 避免大表全表扫描，查询量不超过表行数 25% | 同上游 |
| [2.2.1-14] | 强制 | 禁止只使用全模糊 like，必须有其它等值/范围条件 | 同上游：PG 确需全文检索时用 gin 索引或 pg_trgm |
| [2.2.1-15] | 建议 | 索引列不要使用函数或表达式 | 部分适用：PG 支持表达式索引，但索引表达式必须与查询表达式严格一致才生效 |
| [2.2.1-16] | 建议 | 减少 or，可改写为 union 并分别建索引 | 同上游：PG 也可依赖 BitmapOr，最终以 EXPLAIN 实测为准 |
| [2.2.1-17] | 建议 | 深分页用 where id > 10000 limit 20 改写 limit 10000,20 | 同上游：keyset 分页 |
| [2.2.2-1] | 强制 | 禁止跨 DB 的 join | 部分适用：PG 同一 database 内 schema 之间 join 属正常用法，禁止的是跨 database 的 FDW/远程 join |
| [2.2.2-2] | 强制 | 禁止在更新类 SQL 中使用 join | 部分适用：PG 的 UPDATE ... FROM 语法合法，但要求小批量并先在只读环境验证执行计划 |
| [2.2.2-3] | 建议 | 不建议子查询，拆开结合程序多次查询或改 join | 不适用（改写）：PG 中 IN (SELECT ...)、EXISTS、NOT EXISTS 可正常使用（官方未承诺半连接/子查询提升，属经验性判断），见下方裁决 2 |
| [2.2.2-4] | 建议 | 线上多表 join 不超过 3 个表 | 同上游 |
| [2.2.2-5] | 建议 | 多表连接使用别名，db.表 形式引用字段 | 同上游：PG 为 schema.表 形式 |
| [2.2.2-6] | 建议 | 选取结果集较小的表作为驱动表 | 同上游 |
| [2.2.3-1] | 建议 | 事务内 DML 行数 2000 以内，in 参数 500 以内 | 同上游 |
| [2.2.3-2] | 建议 | 批量操作控制间隔，必要 sleep 5-10 秒 | 同上游 |
| [2.2.3-3] | 建议 | 有 auto_increment 字段的表插入并发控制在 200 以内 | 同上游：PG identity 取值无表级自增锁，瓶颈在 WAL 与索引维护 |
| [2.2.3-4] | 强制 | 必须考虑隔离级别影响（脏读/不可重复读/幻读），建议 repeatable-read | 改写：PG 默认 read committed；需快照一致性用 repeatable read（快照隔离）；需串行化正确性用 serializable（SSI）并必须实现事务重试（40001） |
| [2.2.3-5] | 建议 | 事务内包含 SQL 不超过 5 个（支付业务除外） | 同上游 |
| [2.2.3-6] | 建议 | 事务内更新基于主键或 unique key，否则产生间隙锁 | 改写：PG 无间隙锁，但非索引条件更新会全表扫描、长时间持锁并阻碍 VACUUM，故仍要求基于主键/唯一键 |
| [2.2.3-7] | 建议 | 把外部调用移出事务，避免长事务 | 同上游 |
| [2.2.3-8] | 建议 | 对主从延迟敏感的 select 开启事务强制读主库 | 同上游 |
| [2.2.4-1] | 建议 | 减少 order by，或把排序放到程序端 | 同上游：PG 大排序会溢出到临时文件，需看 EXPLAIN 的 sort/hash 节点与 work_mem |
| [2.2.4-2] | 建议 | order by/group by/distinct 尽量利用索引直接取有序数据 | 同上游 |
| [2.2.4-3] | 建议 | 含排序分组的查询结果集保持在 1000 行以内 | 同上游 |
| [2.2.5-1] | 高危 | 禁用带 limit 的 update/delete，会导致主从不一致，建议加 order by PK | 改写：PG 语法不支持 UPDATE/DELETE ... LIMIT，用 CTE + ctid 或主键子查询分批，或用 FOR UPDATE SKIP LOCKED；ctid 在 UPDATE/VACUUM FULL 后会变化、不能作行标识，CTE + ctid 写法必须逐批重跑 |
| [2.2.5-2] | 高危 | 禁止关联子查询（异议：MySQL 8.0 子查询优化已大幅提升） | 见下方裁决 2：PG 中 IN (SELECT ...)、EXISTS、NOT EXISTS 可正常使用，避免 NOT IN (子查询)（NULL 语义陷阱），以 EXPLAIN (ANALYZE, BUFFERS) 为准 |
| [2.2.5-3] | 强制 | 禁用 procedure、function、trigger、views、event、外键约束 | 部分不适用：PG 中声明式外键默认启用（见下方裁决 3），只读视图可安全使用，触发器与存储过程需评审 |
| [2.2.5-4] | 强制 | 禁用 insert ... on duplicate key update，高并发下主从不一致 | 改写：PG 用 INSERT ... ON CONFLICT DO UPDATE（≥9.5）/ DO NOTHING；无独立错误时 DO UPDATE 保证 INSERT-or-UPDATE 原子结果，仅 SSI 序列化失败、死锁或 arbiter 唯一索引并发重建时才需重试 |
| [2.2.5-5] | 强制 | 禁止联表更新 update t1, t2 where t1.id = t2.id | 改写：PG 改写为 UPDATE ... FROM 或先查后改，必须小批量且走索引 |

## 条款冲突裁决（4 条，不计入上方 109 行）

1. **enum/set（对应 [2.1.5-4] 及其异议）**：上游建议 tinyint，异议建议 enum + 严格模式。PG 结论：优先 text + CHECK (col IN (...))，或原生 enum（支持 ALTER TYPE ... ADD VALUE，但删除/重排枚举值困难、新值同事务内不可用）；状态字段量大且取值稳定时用 smallint + 应用层字典，并用 COMMENT ON COLUMN 记录取值含义；三种方案都必须写明变更成本。
2. **关联子查询（对应 [2.2.5-2] 及其异议）**：上游列为【高危】禁用。PG 结论：IN (SELECT ...)、EXISTS、NOT EXISTS 均可正常使用；官方手册未给出「半连接/反连接与子查询提升」的承诺，属经验性判断，最终以 EXPLAIN (ANALYZE, BUFFERS) 实测为准。仍建议避免 NOT IN (子查询)（NULL 语义陷阱，官方说明见 functions-comparisons）改用 NOT EXISTS。
3. **外键禁令 vs 定义外键（对应 [2.1.4-5]、[2.1.4-7] vs [2.2.5-3]）**：上游强制级自相矛盾（前两条要求定义外键，后者要求禁用外键约束）。PG 结论：默认启用声明式外键，因为被引用列有唯一索引、引用列有索引时写入成本可控，不存在上游担心的隐式全表扫描风险；例外情形须写明理由——超高写入分区表、分片/水平拆分后跨库引用、大批量导入可先 NOT VALID 再 VALIDATE CONSTRAINT 分步上线。上游该禁令的动机（MySQL 时代的实例扩展性与复制约束）在 PG 上不成立。
4. **命名不含数字 vs 分片/日期命名（对应 [2.1.1-3] vs [2.1.2-5]、[2.1.7-10]）**：上游强制级自相矛盾（前者要求名称只用英文字母、不含数字，后者给出 `库通配名_编号` 从 0 递增与按日期分库分表）。PG 结论：把 [2.1.1-3] 读作对业务词根的约束——词根只用英文字母、不含数字；分片序号与日期时间后缀是仅有的两类显式例外（如 northwind_0、log_2026_10），版本号、业务流水号等其余数字段一律不允许；例外后缀不得让标识符以数字开头（PG 未加引号的标识符必须以字母或下划线开头）。
