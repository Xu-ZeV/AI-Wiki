# 计划评审量表（对抗式）

**使用者**：可行性、完整性、范围与对齐三位评审（agent-team-plan-gate）
**用途**：针对用户请求与代码库现实，对实施计划做二元合规验证
**版本**：1.0

---

## 概览

本量表用于**对抗式计划评审**——一种与协作式计划评审根本不同的模式。你的职责是**找出计划中的失败点**，而不是改进它。你在检查计划是否履行了它的契约（用户请求 + 真实代码库），而不是计划"好不好"。

**关键区别：**

- **协作式评审**（协作量表）："这份计划怎么才能更好？" 裁决 APPROVED / NEEDS REVISION。
- **对抗式评审**（本量表）："这份计划是否履行了契约？证明给我看。" 裁决 PASS / FAIL。

---

## 裁决

每次对抗式计划评审只产出唯一一个裁决：

| 裁决 | 含义 | 标准 |
| --- | --- | --- |
| **PASS** | 计划履行了契约 | 未发现任何 BLOCKING 问题 |
| **FAIL** | 计划违反了契约 | 发现一个或多个 BLOCKING 问题 |

没有"带评论通过"，也没有"建议修改"。只有 PASS 或 FAIL。

---

## 问题分类

每个被发现的问题都要归类为 BLOCKING 或 WARNING：

| 分类 | 含义 | 对裁决的影响 |
| --- | --- | --- |
| **BLOCKING** | 契约违反——计划声称 X，代码库却显示不是；或用户要求 X，计划却漏掉了 | 导致 FAIL |
| **WARNING** | 质量顾虑——不构成契约违反，但值得记录 | **不**导致 FAIL |

**拿不准时，按 BLOCKING 处理。** PASS 的门槛应当很高，宁可偏保守地判 FAIL。

---

## 证据要求

每一条发现——无论 PASS 还是 FAIL——都必须附**引用证据**。没有证据的断言无效。

### PASS 的证据（逐条标准）

```markdown
**标准**："全部文件路径存在"
**裁决**：PASS
**证据**：
- 计划引用 `src/services/auth.ts` —— 已用 glob 核实，文件存在
- 计划引用 `src/middleware/rate-limit.ts` —— 已用 glob 核实，文件存在
- 计划引用 `src/utils/token.ts` —— 已用 glob 核实，文件存在
```

### FAIL 的证据（逐条标准）

```markdown
**标准**："全部需求已映射到计划条目"
**裁决**：FAIL（BLOCKING）
**期望**：用户需求"为 API 端点加上限流"应映射到一个计划条目
**实际**：没有任何计划条目处理限流。用户请求第 2 段明确提出了该需求。
计划条目 WU-001 至 WU-004 只覆盖了鉴权、路由、测试和文档。
**证据**：用户请求中的 "...and add rate limiting to all public API endpoints" 没有对应的工作单元。
```

### 无效证据（会被拒绝）

- "计划看起来合理"（没有具体引用）
- "需求似乎都覆盖了"（没有需求到计划条目的映射）
- "文件路径大概没问题"（没有对照代码库核实）
- "和以前成功的计划很像"（类比不是证据）

## 评审类别

### 1. 可行性（可行性评审）

这份计划能不能真正在真实代码库上执行？

| 检查项 | 分类 | 判定标准 |
| --- | --- | --- |
| 文件路径存在 | 造假即 BLOCKING | 计划里的每个文件路径都必须用 glob/grep 对照真实代码库核实 |
| 依赖顺序正确 | 循环或前向引用即 BLOCKING | 工作单元不得依赖后续工作单元的输出；不得有循环依赖 |
| 技术方案契合代码库 | 不兼容即 BLOCKING | 提出的模式、库、框架和约定必须与代码库实际用法一致（读现有代码核实） |
| 无未声明假设 | 关键假设缺失即 BLOCKING | 计划不得暗中依赖不存在的服务、环境变量、配置或基础设施 |
| 构建/测试命令有效 | WARNING | 引用的命令（npm 脚本、测试运行器、构建工具）应存在于 package.json 或等价位置 |

**如何核实：**

1. 对计划里的每个文件路径运行 glob 确认其存在（新文件则确认父目录存在）。
2. 对依赖顺序，追踪依赖图，确认没有环或前向引用。
3. 对技术方案，读同区域的 2-3 个现有文件，确认计划做法一致。
4. 对假设，检查引用的服务、环境变量和配置是否存在。

### 2. 完整性（完整性评审）

计划是否完整覆盖了用户请求的每一个方面？

| 检查项 | 分类 | 判定标准 |
| --- | --- | --- |
| 全部需求已映射 | 存在缺口即 BLOCKING | 从用户请求中提取每条独立需求；逐条映射到计划条目；报告未映射的需求 |
| 已定义验证步骤 | 缺失即 BLOCKING | 每处计划改动都必须说明如何验证其生效（测试名、人工检查或断言） |
| 已考虑边界情况 | 明显缺口即 BLOCKING | 错误场景、空/零值状态、边界条件、并发访问（相关时） |
| 回滚/向后兼容 | WARNING | 计划应说明改动是否可逆，以及是否会破坏现有行为 |
| 跨文件集成点 | 缺失即 BLOCKING | 引用或依赖被改文件的文件必须纳入计划 |

**如何核实：**

1. 读用户原始请求，提取一份编号的独立需求清单。
2. 为每条需求找到处理它的具体计划条目。
3. 以表格呈现映射：需求 -> 计划条目。
4. 任何没有计划条目的需求 = BLOCKING FAIL。
5. 对集成点，用 grep 搜索对被改文件的 import。

### 3. 范围与对齐（范围与对齐评审）

计划的规模是否正中用户真正提出的需求？

| 检查项 | 分类 | 判定标准 |
| --- | --- | --- |
| 契合用户请求 | 偏离即 BLOCKING | 计划范围必须与所提需求对齐——而不是与规划者觉得有趣或想重构的东西对齐 |
| 无范围蔓延 | 存在即 BLOCKING | 无法追溯到用户需求的计划条目即为范围蔓延（除非是必要的技术前置） |
| 无范围不足 | 存在即 BLOCKING | 请求的显然推论被遗漏（例如用户要 API 端点，计划却漏了测试） |
| 复杂度相称 | WARNING | 十行配置改动不应该产出十五个工作单元的庞大计划 |
| 未考虑更简方案 | WARNING | 若存在明显更简单的做法，应予指出 |

**如何核实：**

1. 把用户请求的范围与计划范围对比——两者应当相称。
2. 对每个计划条目，回溯到某条用户需求或某个必要的技术前置。
3. 无法回溯的条目 = 范围蔓延。
4. 通读用户请求，找出计划遗漏的隐含工作。

## 输出格式

每位评审**必须**严格按此格式输出：

```markdown
## [评审角色名] — [PASS/FAIL]

### 证据
- [发现 1]：[file:line、glob 结果，或带证据的具体缺口]
- [发现 2]：[file:line、glob 结果，或带证据的具体缺口]
- ...

### 裁决
[PASS：全部标准满足——未发现 BLOCKING 问题]
或
[FAIL：{带证据的 BLOCKING 问题编号列表}]
```

---

## 评审行为准则

1. **以用户请求和代码库现实为准，不以自己的偏好为准。** 如果用户要的是 REST API，计划描述的也是 REST API，那就是 PASS——即使你更喜欢 GraphQL。
2. **不提建议。** 这不是协作式评审。只报 PASS 或 FAIL 并附证据，别的都不说。
3. **不宽容。** "差不多了"就是 FAIL。用户请求就是契约。
4. **不锚定。** 如果是在 FAIL 之后复审，你应当对上一次评审一无所知。如果你知道，你就不是全新评审——把这一点上报给编排者。
5. **无证据即沉默。** 如果你不能引用具体的文件路径、glob 结果、用户需求或计划条目，就不能下这个论断。
6. **独立。** 你不知道其他评审发现了什么，也不要猜测其他评审的裁决。你的评审独立成立。

## 对照：协作式 vs 对抗式计划评审

| 维度 | 协作式 | 对抗式（本量表） |
| --- | --- | --- |
| **目标** | 提升计划质量 | 验证计划是否合规 |
| **裁决** | APPROVED / NEEDS REVISION | PASS / FAIL |
| **证据** | 有帮助但可选 | 强制（文件路径、需求、计划条目） |
| **建议** | 鼓励 | 禁止 |
| **复审** | 同一评审聚焦此前识别的问题 | 必须全新评审——不带任何历史上下文 |
| **语气** | 协作伙伴 | 独立审计员 |
| **评审人数** | 1（CTO 角色） | 3（可行性、完整性、范围与对齐） |
| **使用时机** | 单评审的计划质量检查 | 把计划交给用户之前的门禁 |

## Codex 原生落地要点

- 三位评审各自是一个独立 `spawn_agent` 实例，`fork_context=false`，互不可见。
- 模型在 `DeepSeek-V4.1-Flash`（`low`/`medium`/`high`/`xhigh`）与 `ccs-glm-5-3-flash/GLM-5.3-Flash`（`low`/`high`/`max`）之间交错分配。
- 同一模型的多实例**不算异构**，只能算多视角；异构度受限于本机只有两个模型，应在汇总中如实标注。
- 复审一律重新派发全新实例，绝不把上一轮发现写进新提示词。
