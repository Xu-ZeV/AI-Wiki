# 计划评审门禁（Plan Review Gate）

**核心原则**：任何计划在交给用户之前，必须先通过独立的对抗式审查。

## 何时使用

以下任一情况发生时启用本 skill：

1. 任何实施计划（由规划者、探索者或编排者产出）刚刚定稿，尚未呈现给用户。
2. 上游的"编写计划"环节完成了一份计划。
3. 编排流程的计划校验阶段产出了可评审的计划。
4. 用户显式要求："评审这份计划""跑一遍计划门禁""plan review"。

**不适用场景**：琐碎改动不走门禁。单文件缺陷修复、文案订正、配置微调等，都无需评审。只有当计划包含 **≥2 个工作单元** 或 **触及 ≥3 个文件** 时，才值得启用门禁评审。

**授权说明**：调用本 skill 即视为用户已授权派子代理。官方默认规则要求"除非用户或 `AGENTS.md`/skill 明确要求，否则不得派子代理"，本 skill 的显式调用满足该条件，评审期间可以自由使用 `spawn_agent`。

## 目的

当一份实施计划完成草拟、但尚未呈现给用户时，本 skill 自动启用。它并行派发三个独立的对抗式评审角色——可行性（Feasibility）、完整性（Completeness）、范围与对齐（Scope & Alignment）——每个角色一个全新的子代理实例。三者必须全部 PASS。一旦有 FAIL，规划者吸收反馈并重新提交给**完全全新**的评审实例。门禁反复迭代，直到达成一致或达到最大轮次。

## 模型与角色分配（Codex 语境）

本机只有两个可用模型：

| 模型标识 | 显示名 | 规格 | 支持的 reasoning_effort |
| --- | --- | --- | --- |
| `DeepSeek-V4.1-Flash` | DeepSeek-V4.1-Flash | 256K | `low` / `medium` / `high` / `xhigh` |
| `ccs-glm-5-3-flash/GLM-5.3-Flash` | GLM-5.3-Flash | 1M | `low` / `high` / `max` |

同一轮内，每个评审角色都必须是一个全新的子代理实例，模型在两个可用模型之间交错分配：

| 评审角色 | 第 1 轮模型 | reasoning_effort |
| --- | --- | --- |
| 可行性 Reviewer | `DeepSeek-V4.1-Flash` | `high` |
| 完整性 Reviewer | `ccs-glm-5-3-flash/GLM-5.3-Flash` | `high` |
| 范围与对齐 Reviewer | `DeepSeek-V4.1-Flash` | `xhigh` |

进入下一轮复审时，把角色的模型分配**对调**（例如可行性与完整性互换模型），让每个角色在不同轮次被不同模型审查，尽量扩大跨模型的覆盖。

**必须写明的局限**：同一模型跑多个实例**不算异构**，只能算同一模型的多个视角。异构度受限于本机只有两个模型，因此三评审阵容中必然存在一个模型被使用两次的情况。这个局限要在门禁汇总里如实标注，不能把"多实例"包装成"多模型"。

## 三位对抗式评审

每位评审都是一个全新的子代理实例，对代码库只有只读访问权。评审只输出由证据支撑的二元 PASS/FAIL 裁决，不提改进建议，只报事实发现。

### 评审 1：可行性（Feasibility）

这份计划到底能不能在真实代码库上执行？

| 检查项 | 分类 | 判定标准 |
| --- | --- | --- |
| 文件路径存在 | 造假即 BLOCKING | 计划引用的每个文件路径都必须真实存在（用 glob/grep 核对） |
| 依赖顺序正确 | 循环依赖或前向引用即 BLOCKING | 工作单元只能依赖已存在、或在其之前创建的东西 |
| 技术方案契合代码库 | 不兼容即 BLOCKING | 计划提出的模式、库、约定必须与代码库实际用法一致 |
| 无未声明假设 | 关键假设缺失即 BLOCKING | 计划不得暗中依赖并不存在的服务、环境变量或基础设施 |
| 文件范围现实 | WARNING | 每个工作单元的文件范围可以在不引发连锁改动的前提下完成 |

### 评审 2：完整性（Completeness）

计划是否完整覆盖了用户请求的每一个方面？

| 检查项 | 分类 | 判定标准 |
| --- | --- | --- |
| 全部需求已映射 | 存在缺口即 BLOCKING | 用户的每条需求都至少对应一个计划条目 |
| 已定义验证步骤 | 缺失即 BLOCKING | 每处改动都有验证其生效的方式（测试、人工检查或断言） |
| 已考虑边界情况 | 明显缺口即 BLOCKING | 错误场景、空状态、边界条件都已覆盖 |
| 回滚/向后兼容 | WARNING | 计划考虑了改动需要回退时会发生什么 |
| 跨文件集成点 | 缺失即 BLOCKING | 引用了被改文件的依赖方都已纳入计划 |

### 评审 3：范围与对齐（Scope & Alignment）

计划的规模是否正中用户真正提出的需求？

| 检查项 | 分类 | 判定标准 |
| --- | --- | --- |
| 契合用户请求 | 偏离即 BLOCKING | 计划解决的是用户提出的问题，而不是规划者觉得有趣的问题 |
| 无范围蔓延 | 存在即 BLOCKING | 没有超出请求的多余功能、抽象或重构 |
| 无范围不足 | 存在即 BLOCKING | 请求的显然推论没有被遗漏 |
| 复杂度相称 | WARNING | 方案复杂度与问题复杂度相匹配 |
| 未遗漏更简方案 | WARNING | 当更简单的做法足以达成目标时，计划没有过度设计 |

## 评审隔离五规则

以下规则**强制生效**，违反任何一条即判定本次评审无效：

1. **只用全新实例。** 每位评审都是一个新 `spawn_agent` 实例——绝不复用、绝不续接、绝不给轮次之间的上下文。
2. **评审之间互不可见。** 任何一位评审都不得看到另一位评审的输出。永远不行。
3. **代码库只读。** 评审可以读文件、可以跑 grep/glob，但不能修改任何东西。
4. **复审不带历史发现。** 迭代后重新评审时，必须派发完全全新的实例；新评审对之前评审发现了什么一无所知。
5. **输入仅限三项：** 计划正文、用户的原始请求、代码库（通过只读工具访问）。

**为什么隔离如此重要**：看过此前发现的评审会锚定在那些发现上，而不是独立复查。全新实例可以消除这种偏差，确保每一轮评审都是真正独立的检查。在 Codex 中还有一层原因：子代理默认不继承父会话历史，也不互相可见，这天然满足规则 2 和规则 4，但前提是提示词里**不得**夹带上一轮的发现。

## 工作流

```text
1. 规划者/探索者/编排者产出计划草稿
2. 并行派发 3 个对抗式评审（全新 spawn_agent 实例）
3. 收集全部 3 份裁决
4. 若全部 PASS ——> 连同门禁通过摘要一起呈现给用户
5. 若任一 FAIL ——>
   a. 规划者阅读全部评审的全部反馈
   b. 规划者吸收修改，或记录该反馈不适用的理由
   c. 派发 3 个全新评审实例（绝不复用，避免锚定）
   d. 从第 3 步重复
6. 最多 3 轮 ——> 连同遗留问题一起呈现给用户决策
```

### 阶段 1：派发评审（并行）

用同一条消息里的三个 `spawn_agent` 调用实现并行；`fork_context=false` 保证每个评审都是干净起点。

```text
spawn_agent(
  message=<可行性评审提示词 + 计划正文 + 用户原始请求>,
  model="DeepSeek-V4.1-Flash",
  reasoning_effort="high",
  fork_context=false)

spawn_agent(
  message=<完整性评审提示词 + 计划正文 + 用户原始请求>,
  model="ccs-glm-5-3-flash/GLM-5.3-Flash",
  reasoning_effort="high",
  fork_context=false)

spawn_agent(
  message=<范围与对齐评审提示词 + 计划正文 + 用户原始请求>,
  model="DeepSeek-V4.1-Flash",
  reasoning_effort="xhigh",
  fork_context=false)
```

拿到返回的 target 后统一等待：

```text
wait_agent(targets=[可行性, 完整性, 范围与对齐], timeout_ms=600000)
```

### 阶段 2：判定门禁

```text
IF 可行性.verdict === "PASS"
   AND 完整性.verdict === "PASS"
   AND 范围与对齐.verdict === "PASS":
  --> 门禁通过。把计划呈现给用户。

ELSE:
  --> 汇总全部 FAIL 发现。
  --> 交给规划者修订。
  --> 迭代计数 +1。
  --> IF 迭代数 >= 3: 连同遗留问题一起呈现给用户。
  --> ELSE: 对修订后的计划派发全新评审。
```

### 阶段 3：迭代（出现 FAIL 时）

1. 规划者接收来自**所有**评审（含 PASS 与 FAIL）的汇总反馈。
2. 规划者修订计划，逐条处理每个 FAIL 发现。
3. 对每个发现，规划者只能二选一：
   - **修复**——修改计划以解决该问题。
   - **反驳**——用证据说明该发现不正确或不适用。
4. 为复审派发 3 个**完全全新**的 `spawn_agent` 实例。
5. 新评审只看到修订后的计划和原始请求——**不得**看到此前的发现。
6. 先用 `close_agent(target=<上一轮各实例>)` 关闭上一轮实例，再派发新实例，避免残留上下文被误用。

### 阶段 4：升级（3 轮之后）

如果门禁在 3 轮之后仍未达成一致：

```markdown
## 计划评审门禁：需要升级决策（3/3 轮已用尽）

### 遗留的 BLOCKING 问题

#### 可行性
- [带证据的问题]

#### 完整性
- [带证据的问题]

#### 范围与对齐
- [带证据的问题]

### 迭代历史
| 轮次 | 可行性 | 完整性 | 范围与对齐 |
|------|--------|--------|-----------|
| 1    | FAIL   | PASS   | FAIL      |
| 2    | PASS   | PASS   | FAIL      |
| 3    | PASS   | PASS   | FAIL      |

### 可选处置
1. **覆盖**——按现状推进（遗留问题记为已知风险）
2. **修订**——继续人工迭代计划
3. **简化**——缩减范围，去掉争议条目
4. **取消**——放弃该计划，重新开始

请选择一项处置，或补充更多上下文。
```

## Codex 原生落地

### 编排顺序

1. **定稿计划**：确认计划正文已经稳定，并把它连同用户原始请求一起准备好。
2. **并行派发**：在同一条消息里发出 3 个 `spawn_agent` 调用（可行性 / 完整性 / 范围与对齐），`fork_context=false`。
3. **统一等待**：用一次 `wait_agent(targets=[...], timeout_ms=600000)` 等待三个 target 全部结束。
4. **判定**：读三份裁决，执行阶段 2 的二元判定。
5. **FAIL 迭代**：若失败，先 `close_agent` 关掉旧实例，再对修订稿派发 3 个全新实例。
6. **收尾**：全部 PASS 或达到 3 轮上限后，`close_agent` 关闭所有仍在运行的评审实例。

### `spawn_agent` 参数要点

- `message`：必须**自包含**。子代理默认不带父会话历史，提示词里要包含完整计划正文、用户原始请求，以及"你正在独立评审"的说明。
- `model`：在两个可用模型之间交错分配，见上文"模型与角色分配"。
- `reasoning_effort`：可行性/完整性用 `high`，范围与对齐用 `xhigh`；GLM 侧若要更强推理可用 `max`。注意各模型支持的档位不同，不要给 GLM 传 `xhigh`、不要给 DeepSeek 传 `max`。
- `fork_context`：计划评审门禁固定为 `false`，这是隔离规则 1、2、4 的落地方式。

### 编排顺序示例

```text
# 第 1 轮
t1 = spawn_agent(message=可行性提示词, model="DeepSeek-V4.1-Flash", reasoning_effort="high", fork_context=false)
t2 = spawn_agent(message=完整性提示词, model="ccs-glm-5-3-flash/GLM-5.3-Flash", reasoning_effort="high", fork_context=false)
t3 = spawn_agent(message=范围与对齐提示词, model="DeepSeek-V4.1-Flash", reasoning_effort="xhigh", fork_context=false)
results = wait_agent(targets=[t1, t2, t3], timeout_ms=600000)

# 若任一 FAIL，先关闭再重新派发（模型对调，且不带历史发现）
close_agent(t1); close_agent(t2); close_agent(t3)
```

## 评审提示词

每个提示词都要以"你的任务是找出问题，而不是批准"开头，并附上完整的计划正文与用户原始请求。

## 输出结构

### 单评审输出

每位评审严格按此格式输出：

```markdown
## [评审角色名] — [PASS/FAIL]

### 证据
- [发现 1]：[file:line 引用，或带证据的具体缺口]
- [发现 2]：[file:line 引用，或带证据的具体缺口]
- ...

### 裁决
[PASS：全部标准满足——未发现 BLOCKING 问题]
或
[FAIL：{带证据的 BLOCKING 问题编号列表}]
```

### 门禁汇总输出（全部 PASS）

```markdown
## 计划评审门禁 — 通过（第 N 轮 / 共 3 轮）

| 评审角色 | 裁决 | 关键发现 | 本轮模型 |
|----------|------|----------|----------|
| 可行性 | PASS | 全部文件路径已核实，依赖顺序正确 | DeepSeek-V4.1-Flash |
| 完整性 | PASS | 全部 N 条需求已映射到计划条目 | GLM-5.3-Flash |
| 范围与对齐 | PASS | 计划契合用户请求，无范围蔓延 | DeepSeek-V4.1-Flash |

异构度说明：本机仅有两个可用模型，本轮存在同一模型被两个角色使用的情况，属于多视角而非完全异构。

计划已可提交用户评审。
```

### 门禁汇总输出（存在 FAIL）

```markdown
## 计划评审门禁 — 需要修订（第 N 轮 / 共 3 轮）

| 评审角色 | 裁决 | BLOCKING 问题 |
|----------|------|---------------|
| 可行性 | PASS | —— |
| 完整性 | FAIL | 2 个 BLOCKING 问题 |
| 范围与对齐 | FAIL | 1 个 BLOCKING 问题 |

### BLOCKING 问题（必须处理）

#### 完整性评审
1. **缺需求映射**：用户要求 X，但没有任何计划条目覆盖它
2. **WU-003 缺验证**：该计划条目没有定义测试或断言

#### 范围与对齐评审
1. **范围蔓延**：WU-005 加入了用户未要求的缓存层

---

**轮次**：第 N 轮 / 共 3 轮
**需要动作**：规划者必须处理全部 BLOCKING 问题后重新提交。
```

## 反模式

| # | 反模式 | 为什么错 | 正确做法 |
| --- | --- | --- | --- |
| 1 | **复用评审实例**——把发现传递给下一轮评审 | 锚定偏差：评审会去核对上一轮的发现，而不是独立复查 | 派发不带任何历史上下文的新 `spawn_agent` 实例 |
| 2 | **评审之间串味**——把一位评审的输出给另一位看 | 破坏独立性；评审会趋同而不是各自独立检查 | 每位评审只看到：计划、用户请求、代码库 |
| 3 | **把 FAIL 当参考**——"评审虽然没过，但问题不大" | 架空门禁，等同于没有门禁 | FAIL 就意味着修订并重新评审，没有例外 |
| 4 | **对"简单"计划跳门禁**——"这个很直白，不用评了" | "简单"与否正是门禁要验证的判断 | 只要计划有 2+ 个工作单元或触及 3+ 个文件，就跑门禁 |
| 5 | **规划者自评**——写计划的 agent 自己评审自己 | 确认偏差；规划者会批准自己的产出 | 评审必须是独立于规划者的全新子代理实例 |
| 6 | **无限迭代**——"一直评到过为止" | 收益递减；3 轮之后往往说明是计划本身有根本问题 | 最多 3 轮，然后带上完整上下文升级给用户 |
| 7 | **部分复审**——只重跑失败的那位评审 | 其他评审也可能在修订稿上失败 | 每一轮都对全部 3 位评审重新派发全新实例 |
| 8 | **把多实例当多模型**——声称"三路异构评审" | 同一模型的多实例不是异构，只是多视角 | 如实标注异构度受限于本机只有两个模型 |

## 集成点

### 上游（本门禁的输入）

- "编写计划"环节——产出的计划喂给本门禁。
- 编排流程的计划校验——预检清单在本门禁之前运行。
- 规划者/探索者直接草拟的计划。

### 下游（门禁通过之后）

- 把计划呈现给用户做最终确认。
- **用户批准之后**：把已批准的计划落盘到 `docs/plans/active-plan.md`（见下文「计划落盘」）。
- 用户批准的计划进入编排执行阶段。
- 工作单元拆分与实现开始。

### 计划落盘

门禁通过**且**用户批准计划之后，把计划落盘，使其在上下文压缩后依然可恢复：

```bash
mkdir -p docs/plans

# 写入带元数据头的计划文件
cat > docs/plans/active-plan.md << 'PLAN_EOF'
# 当前计划
<!-- approved: <timestamp> -->
<!-- gate-iterations: <N> -->
<!-- user-approved: true -->
<!-- status: in-progress -->

<完整批准后的计划正文>
PLAN_EOF
```

评审过程记录建议落到 `docs/plans/review-gate-<topic>.md`，包含每轮的三份裁决与最终结论。这样即使 agent 在执行中途丢失上下文，也可以从磁盘重读已批准的计划，而不必重跑整轮门禁。

### 与设计评审门禁的关系

- **设计评审门禁**（`agent-team-design-gate`）评审*设计文档*，使用 5 位专业评审（产品经理、架构师、设计师、安全、CTO），裁决为 APPROVED/NEEDS_REVISION。
- **计划评审门禁**（本 skill）评审*实施计划*，使用 3 位对抗式评审（可行性、完整性、范围与对齐），裁决为二元 PASS/FAIL。

两者是不同阶段的互补门禁：
1. 设计评审门禁验证*要做什么*。
2. 计划评审门禁验证*怎么做*。
3. 编排执行验证*是否做对了*。

## 成功标准

计划评审门禁在满足以下条件时算成功：

- [ ] 三位评审全部返回 PASS 裁决。
- [ ] 全部 BLOCKING 问题均已带证据地解决。
- [ ] 计划连同门禁通过摘要一起呈现给用户。
- [ ] 评审隔离得到保持（全新实例、无交叉污染）。
- [ ] 门禁在 3 轮之内完成。
