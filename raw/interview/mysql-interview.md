## 一、索引基础与回表

### MySQL 中索引的作用是什么？为什么索引能提高查询效率？

题目：

请你讲一下：

> MySQL 中索引的作用是什么？为什么索引能提高查询效率？

**标准回答**

MySQL 索引的作用是提高查询效率，减少全表扫描。InnoDB 的索引底层主要使用 B+ 树，B+ 树高度较低，可以减少磁盘 IO，并且叶子节点有序，适合范围查询和排序。

对于主键索引，叶子节点存储整行数据；对于二级索引，叶子节点存储索引字段和主键值。如果查询字段不在二级索引中，就需要根据主键再回到聚簇索引中查询整行数据，这个过程叫回表。如果查询字段都包含在索引中，就形成覆盖索引，可以直接从索引中返回结果，避免回表。

**回答要点**

- 索引的核心作用是加快查询，减少扫描行数。
- InnoDB 索引底层主要是 B+ 树。
- B+ 树高度低，有利于减少磁盘 IO。
- B+ 树叶子节点有序，适合范围查询和排序。
- 主键索引是聚簇索引，叶子节点存储整行数据。
- 二级索引叶子节点存储索引字段和主键值。
- 二级索引查询非索引字段时可能需要回表。
- 覆盖索引可以避免回表。

**常见误区**

- 覆盖索引不是回表，而是避免回表。
- 普通索引、二级索引查询整行数据时才可能发生回表。
- 面试中建议使用“联合索引”或“组合索引”，不要说成“组件索引”。

### InnoDB 中，聚簇索引和二级索引有什么区别？为什么通过普通索引查询有时候需要回表？

题目：

请你说一下：

> InnoDB 中，聚簇索引和二级索引有什么区别？为什么通过普通索引查询有时候需要回表？

**标准回答**

InnoDB 中，聚簇索引通常就是主键索引，一个表只能有一个聚簇索引。聚簇索引的叶子节点存储整行数据，所以通过主键查询时，可以直接在聚簇索引中定位并拿到完整记录。

二级索引也叫辅助索引，普通索引、唯一索引、联合索引等非主键索引都属于二级索引。二级索引的叶子节点存储的是索引字段值和对应的主键值，而不是整行数据。

通过普通索引查询时，如果查询需要的字段都在二级索引中，就可以直接返回结果，这叫覆盖索引，不需要回表。如果查询需要的字段不在二级索引中，MySQL 就需要先从二级索引中找到主键值，再根据主键值回到聚簇索引查询整行数据，这个过程叫回表。

**回答要点**

- 聚簇索引通常是主键索引，一个 InnoDB 表只能有一个聚簇索引。
- 聚簇索引叶子节点存储整行数据。
- 二级索引叶子节点存储索引字段值和主键值。
- 普通索引、唯一索引、联合索引等非主键索引通常都是二级索引。
- 二级索引不是一定回表，只有查询字段不被索引覆盖时才需要回表。
- 覆盖索引可以避免回表。

**常见误区**

- 建议说“聚簇索引”，不要说成“聚集索引”或“主表索引”。
- 二级索引叶子节点不只存当前索引字段，还会存主键值。
- 二级索引不等于“必须回表的索引”，是否回表取决于查询字段是否被索引覆盖。

### 什么是回表？什么是覆盖索引？实际开发中怎么利用覆盖索引优化查询？

题目：

请你讲一下：

> 什么是回表？什么是覆盖索引？实际开发中怎么利用覆盖索引优化查询？

**标准回答**

回表是指通过二级索引查询数据时，如果二级索引中没有包含查询所需的全部字段，MySQL 需要先从二级索引中找到主键值，再根据主键值回到聚簇索引中查询整行数据。

覆盖索引是指查询需要的字段都已经包含在索引中，MySQL 可以直接从索引中返回结果，不需要再回到聚簇索引查询整行数据。覆盖索引不是一种单独的索引类型，而是一种查询命中索引后的现象。

实际开发中，可以通过合理设计联合索引来减少回表。例如经常执行：

```sql
SELECT name, age
FROM user
WHERE name = 'Tom';
```

可以建立联合索引：

```sql
CREATE INDEX idx_name_age ON user(name, age);
```

这样 `name` 用于查询过滤，`age` 也在索引中，查询 `name` 和 `age` 时就可以直接走覆盖索引，避免回表。

**回答要点**

- 回表通常发生在通过二级索引查询非索引字段时。
- 二级索引叶子节点存储索引字段和主键值。
- 覆盖索引要求查询字段全部包含在索引中。
- 覆盖索引可以减少一次聚簇索引查询，降低随机 IO。
- 实际优化时应避免 `SELECT *`，只查询业务需要的字段。
- 可以围绕 `WHERE`、`ORDER BY`、`GROUP BY` 和返回字段设计联合索引。
- 不要为了覆盖索引盲目把大量字段都放进索引，尤其是大字段或频繁更新字段。

**常见误区**

- 覆盖索引不是“索引类型”，而是查询是否被索引覆盖的结果。
- 二级索引不是一定回表，只有查询字段不在索引中时才需要回表。
- 设计覆盖索引要考虑写入成本和索引体积，不能只看查询性能。

## 二、索引失效与设计

### MySQL 中哪些情况会导致索引失效？请至少说 5 种，并举例说明。

题目：

请你讲一下：

> MySQL 中哪些情况会导致索引失效？请至少说 5 种，并举例说明。

**标准回答**

MySQL 中常见的索引失效或索引效果变差场景包括：联合索引不满足最左前缀原则、对索引字段使用函数、对索引字段进行计算、字符串字段查询时没有加引号导致隐式类型转换、`LIKE` 左模糊、`OR` 条件中有字段没有索引，以及一些负向条件导致优化器认为走索引成本更高。

需要注意，范围查询不是完全不能使用索引。范围查询通常可以用到当前字段的索引，但在联合索引中，范围查询字段后面的字段通常不能继续用于索引定位。

**示例**

**不满足最左前缀原则**

```sql
-- 索引是 (a, b, c)
SELECT * FROM t WHERE b = 2;
```

跳过了最左字段 `a`，通常不能有效使用该联合索引。

**对索引字段使用函数**

```sql
SELECT * FROM user WHERE LOWER(name) = 'tom';
```

对 `name` 使用函数后，可能导致索引失效。

**对索引字段进行计算**

```sql
SELECT * FROM user WHERE age + 1 = 19;
```

可以改成：

```sql
SELECT * FROM user WHERE age = 18;
```

**字符串字段不加引号**

```sql
-- phone 是 varchar 类型
SELECT * FROM user WHERE phone = 13800138000;
```

可能发生隐式类型转换，导致索引失效或索引效果变差。应写成：

```sql
SELECT * FROM user WHERE phone = '13800138000';
```

**LIKE 左模糊**

```sql
SELECT * FROM user WHERE name LIKE '%tom';
```

左模糊无法利用 B+  树索引的有序性。右模糊通常可以使用索引：

```sql
SELECT * FROM user WHERE name LIKE 'tom%';
```

**OR 条件中有字段没有索引**

```sql
SELECT * FROM user WHERE name = 'Tom' OR address = '北京';
```

如果 `address` 没有索引，可能导致整体索引效果变差。

**负向查询**

```sql
SELECT * FROM user WHERE status != 1;
```

`!=`、`<>`、`NOT IN` 等条件可能导致优化器认为走索引成本较高，从而不走索引，具体要看数据分布和执行计划。

**回答要点**

- 联合索引要满足最左前缀原则。
- 不要在索引字段上使用函数或计算。
- 字符串类型字段查询时要加引号，避免隐式类型转换。
- `LIKE '%xxx'` 左模糊通常无法有效使用 B+ 树索引。
- `OR` 条件中部分字段无索引时，可能影响整体索引使用。
- 负向条件不一定绝对索引失效，但经常导致索引效果不好。
- 范围查询不是不能用索引，而是范围字段后面的联合索引字段通常不能继续用于索引定位。

**常见误区**

- 不要简单说“范围查询会导致索引失效”，更准确是“范围查询字段后面的联合索引字段通常不能继续用于索引定位”。
- 索引是否真正失效要结合 `EXPLAIN` 和数据分布判断，不能只背规则。
- SQL 条件书写顺序不等于联合索引字段顺序，优化器可能会调整条件顺序，关键是是否能从联合索引最左侧连续匹配。

### 实际开发中，你会怎么给一张表设计索引？哪些字段适合建索引，哪些字段不适合？索引是不是越多越好？

题目：

请你讲一下：

> 实际开发中，你会怎么给一张表设计索引？哪些字段适合建索引，哪些字段不适合？索引是不是越多越好？

**标准回答**

实际开发中设计索引，首先要看真实查询场景。经常出现在 `WHERE`、`JOIN ON`、`ORDER BY`、`GROUP BY` 中的字段比较适合建索引。其次要看字段区分度，手机号、订单号、身份证号这类区分度高甚至唯一的字段很适合建唯一索引；`user_id`、`company_id`、`create_time` 这类字段虽然不唯一，但如果查询频繁，也适合建普通索引或联合索引。

不适合建索引的字段包括：低频查询字段、区分度很低的字段、大文本字段、频繁更新但查询很少的字段。比如性别、简单状态值这类字段单独建索引通常意义不大，但如果它们经常和时间、用户 ID 等字段组合查询，可以考虑设计联合索引。

索引不是越多越好。索引会占用额外存储空间，并且在 `INSERT`、`UPDATE`、`DELETE` 时需要维护索引结构，索引过多会降低写入性能，也会增加优化器选择成本。所以索引设计要围绕核心 SQL 和高频查询来做。

设计联合索引时，要结合最左前缀原则，把高频过滤字段、区分度较高的字段、排序或分组字段合理组合；同时尽量利用覆盖索引，减少回表。但不能为了覆盖索引盲目把大量字段都放入索引，尤其是大字段和频繁更新字段。

**示例**

订单表：

```sql
CREATE TABLE orders (
  id BIGINT PRIMARY KEY,
  order_no VARCHAR(64),
  user_id BIGINT,
  status TINYINT,
  create_time DATETIME
);
```

常见索引设计：

```sql
-- 订单号唯一查询
CREATE UNIQUE INDEX uk_order_no ON orders(order_no);

-- 查询某个用户的订单列表，并按时间排序
CREATE INDEX idx_user_time ON orders(user_id, create_time);

-- 查询某个状态下的近期订单
CREATE INDEX idx_status_time ON orders(status, create_time);
```

如果 `status` 只有少量枚举值，单独给 `status` 建索引通常意义不大，但和 `create_time` 组合后，可能对“按状态查询近期订单”这类场景有价值。

**回答要点**

- 根据真实 SQL 和业务查询场景设计索引。
- 高频出现在 `WHERE`、`JOIN ON`、`ORDER BY`、`GROUP BY` 中的字段适合建索引。
- 区分度高的字段适合建索引，唯一字段适合建唯一索引。
- 主键 `id` 通常天然有主键索引，不需要重复建普通索引。
- 外键或关联字段如 `user_id`、`order_id`、`company_id` 高频查询或关联时通常适合建索引。
- 低频查询字段、低区分度字段、大字段、频繁更新字段不适合盲目建索引。
- 联合索引要结合最左前缀原则和查询条件顺序设计。
- 可以通过覆盖索引减少回表，但要控制索引字段数量。
- 索引不是越多越好，会增加存储成本和写入维护成本。

**常见误区**

- 不是只有唯一字段才适合建索引，非唯一但高频查询的字段也可能很适合。
- 名字、公司名、文件名等字段是否适合建索引，要看查询方式；如果经常 `LIKE '%xxx%'`，普通 B+ 树索引效果不好。
- 主键字段一般已有索引，不要重复创建同样的普通索引。
- 关联字段类型、长度、字符集和排序规则尽量保持一致，避免隐式转换影响索引使用。
- 不要只凭字段名建索引，要结合 `EXPLAIN`、数据量、区分度和查询频率判断。

# 三、锁
1.解释一下锁
面试官您好，我从**粒度**和**模式**两个维度来聊一下MySQL InnoDB的锁机制。

**首先是粒度**，分为全局锁、表级锁和行级锁。**模式上**分为共享锁和排他锁，共享锁就是允许持有锁的事务读数据，其他事务也能读，但是不能修改。排他锁就是允许持有锁的事务修改数据，其他事务既不能读也不能改。

**先说全局锁**，加锁之后整个数据库就变成只读了。比如全库逻辑备份、数据迁移这些需要保证全局数据一致性的操作。加锁期间，DML和DDL都会被阻塞。

**再来说表级锁**，表级锁主要有三类：表锁、元数据锁和意向锁。

**表锁**是通过`LOCK TABLES`命令手动加的，分共享和排他两种。表共享锁是`LOCK TABLES t READ`，允许其他事务读，但阻塞修改。表排他锁是`LOCK TABLES t WRITE`，会阻塞其他所有操作，包括读和写。

**元数据锁**是MySQL 5.5引入的自动锁，为了保证表结构变更和数据操作之间不冲突。当我们执行DML操作时，会自动加MDL读锁，这时候会阻塞DDL操作。反过来，执行DDL操作时会自动加MDL写锁，会阻塞所有DML操作。

**意向锁**是InnoDB自动添加的表级锁，它的作用是作为行锁和表锁之间的桥梁。当给某行加共享锁时，会自动在表级加意向共享锁，也就是IS锁。当给某行加排他锁时，会自动加意向排他锁，也就是IX锁。意向锁的核心价值在于，当需要加表锁时，MySQL不用去遍历所有行记录检查有没有行锁，只需要看一眼表级的意向锁就能快速判断。这里有几个关键点要注意：意向锁之间是互相兼容的，因为它们只是个标记。但是表共享锁和意向排他锁是互斥的，因为表共享锁要保证读取一致性，而IX锁说明有事务正在修改行数据。表排他锁跟所有锁都互斥。

**最后说行级锁**，InnoDB的行级锁是基于索引实现的，锁实际上是加在B+树叶子结点的索引项上。行级锁主要分三类。

**第一类是记录锁**，就是锁定某一条具体的索引记录。这里要注意，如果查询没有走索引，走的是全表扫描，那InnoDB会对表中所有行逐一加记录锁，效果上等同于表锁，但底层还是行锁，这是生产环境需要极力避免的。

**第二类是间隙锁**，它锁定的是索引记录之间的间隙，不包含记录本身。比如说数据有1、5、10，间隙锁可以锁住1到5之间或者5到10之间的范围。它的特点是只阻塞插入操作，不阻塞其他事务对已有记录的修改，主要目的就是防止幻读。

**第三类是临键锁**，它是记录锁加间隙锁的组合，锁定范围是左开右闭。比如数据有1、5、10，锁定id等于5的时候，临键锁的范围就是大于1且小于等于5，既锁住了5这条记录本身，也锁住了1和5之间的间隙。临键锁是InnoDB在可重复读隔离级别下的默认行锁算法，用于彻底解决幻读问题。还有一个降级机制需要提一下，就是当使用唯一索引做等值查询且命中记录时，临键锁会降级为记录锁，只锁那一行，不再锁间隙，这样可以提升并发性能。

以上就是我对MySQL锁机制的整体理解，谢谢面试官。

## 四、MVCC是什么
MVCC（多版本并发控制）主要用于InnoDB在读已提交和可重复读隔离级别下，实现快照读的非阻塞读操作
它的核心由三部分组成：

1、隐藏字段：每行数据有最近修改事务ID和回滚指针，指向Undo Log。
2、Undo Log版本链：每次修改数据时，旧数据的反向操作先写入Undo Log，然后将新数据的DB_ROLL_PTR指向旧版本，形成一条由新到旧的链表。
3、Read View（一致性视图）：它决定了当前事务能看到哪些版本。
在 RC级别，每次快照读都会生成新的Read View。
在 RR级别，只会在第一次快照读时生成Read View，后续复用。
查询时，InnoDB会拿着当前Read View，沿着UndoLog版本链逆向查找，跳过那些对当前事务不可见的版本（比如未提交事务修改的版本），直到找到第一个DB_TRX_ID满足可见性条件的版本，从而保证事务内数据的一致性。
