# RAG 面试文档：如何让 LLM 回答出全面的粗粒度（跨段落）知识？

## 1. 面试题

在基于 LLM + 向量库的文档对话系统中，如何让 LLM 回答出全面的粗粒度知识，尤其是跨段落知识？

典型问题示例：

```text
用户：根据文档内容，征信中心有几点声明？
LLM：根据文档内容，有三点声明，分别是：一、……；二、……；三、……。
```

这个问题考察的不是单纯的 Prompt 编写能力，而是对 RAG 检索链路、文档切分策略、语义召回和上下文构造的综合理解。

## 2. 核心结论

要让 LLM 回答全面的粗粒度、跨段落知识，关键不只是优化 Prompt，而是要优化 RAG 的检索和文档加工流程。

核心方案是：

```text
语义切分文档 -> 抽取关键信息 -> 建立“关键信息 -> 原始文本”的二级索引 -> 检索关键信息 -> 映射回完整原文 -> 交给 LLM 总结回答
```

也就是说，检索阶段负责“找全、找准”，LLM 阶段负责“整合、表达”。如果检索阶段召回的上下文本身就是残缺的，LLM 很难凭空回答完整内容。

## 3. 为什么会出现回答不全面的问题？

在 RAG 文档问答中，LLM 的回答质量高度依赖召回的上下文。

如果用户问的是细粒度问题，例如：

```text
2023 年我国上半年的国内生产总值是多少？
```

这种问题通常只需要召回一个短片段即可回答。

但如果用户问的是粗粒度问题，例如：

```text
征信中心有几点声明？
```

这类问题可能需要跨多个段落才能回答完整。如果向量检索只召回了其中两个段落，LLM 就只能回答两点，而真实文档中可能有三点。

所以这个问题的本质是：

```text
不是 LLM 不会总结，而是检索阶段给 LLM 的上下文不完整。
```

## 4. 为什么不能简单把 Chunk 切大？

一种直觉方案是把文档切分粒度调大，例如每 10 个段落合成一个 chunk。

这种方式虽然能减少信息被切碎的概率，但不是最优解，因为它会带来两个问题。

第一，噪声变多。

chunk 越大，里面包含的无关信息越多。用户只问“三点声明”，但召回片段里可能还混入背景介绍、其他政策说明、无关日期等内容。

第二，LLM 更容易被干扰。

LLM 本身存在幻觉问题。如果上下文中噪声过多，模型可能抓错重点，甚至把无关内容也总结进答案里。

因此，理想的 chunk 不是越大越好，而是：

```text
语义上完整，内容上干净，检索上高相关。
```

## 5. 推荐的整体思路

RAG 文档问答可以拆成两个核心阶段：

```text
先检索，后推理。
```

检索阶段要尽量满足三个目标：

1. 召回率高：与问题相关的内容尽可能都被找出来。
2. 无关信息少：尽量减少噪声内容进入上下文。
3. 速度快：不能为了准确性让检索成本不可接受。

LLM 阶段则负责把已经召回的完整上下文进行整合、归纳和表达。

从工程角度看，RAG 的重点通常不是“让 LLM 更聪明”，而是“让 LLM 拿到更好的上下文”。

## 6. 二级索引方案

文档中提出的关键方案是构建二级索引：

```text
第一级索引：关键信息
第二级索引：原始文本
```

二者一一映射。

检索时，只对“关键信息”做 embedding，并参与相似度计算。召回命中后，再把关键信息对应的“原始文本”交给 LLM。

示意结构如下：

```text
关键信息 A -> 原始文本 A
关键信息 B -> 原始文本 B
关键信息 C -> 原始文本 C
```

举例：

```text
关键信息：
征信中心声明、三点声明、信息安全、异议处理、个人信用报告

原始文本：
包含三点声明的完整原文段落。
```

用户问题：

```text
征信中心有几点声明？
```

系统先用 query 和“关键信息”做相似度匹配，命中后再取出对应原始文本，让 LLM 基于完整上下文回答。

这个设计的好处是：

1. 用关键信息做检索，匹配更聚焦。
2. 用原始文本做回答，信息更完整。
3. 避免直接用大段原文做 embedding 导致语义被稀释。

## 7. 语义切分方案

文档强调，文档切分不能简单依赖 PDF 换行符、HTML 标签或固定长度，而应该进行语义级别的切分。

语义切分的目标是：

```text
把讲同一件事的内容尽量放在同一个语义块中。
```

### 7.1 方法一：篇章分析

可以使用 NLP 中的篇章分析，也就是 discourse parsing。

它的作用是分析段落之间的逻辑关系，例如：

```text
总分关系
解释关系
补充关系
因果关系
主从关系
```

如果多个段落之间存在明显的主从关系或补充关系，就应该合并成一个语义段。

这样处理后，每个语义段尽量只表达一个完整主题，后续检索时更容易召回完整内容。

### 7.2 方法二：基于 BERT 的相邻段落判断

还可以借助 BERT 等模型判断相邻句子或相邻段落是否存在语义衔接。

BERT 在预训练阶段使用过 NSP，也就是 next sentence prediction，能够判断两个句子是否上下文连续。

工程上可以设置一个阈值，从前往后判断：

```text
如果相邻段落语义相关度大于阈值，就合并。
如果相邻段落语义相关度小于阈值，就断开。
```

这种方式比固定长度切分更灵活，也更接近人类阅读文档时对主题边界的判断。

## 8. 关键信息如何抽取？

语义块切好之后，还需要从语义块中抽取关键信息，作为向量检索的索引内容。

常见方法包括以下几类。

### 8.1 成分句法分析

成分句法分析可以提取句子中的核心结构，例如名词短语、动词短语等。

例如：

```text
原始文本：
MM 团队的成员都是精英，核心成员是前谷歌高级产品经理张三，前 Meta 首席技术官李四。

关键信息：
MM 团队、核心成员、张三、李四
```

### 8.2 命名实体识别

命名实体识别可以提取重要实体，例如：

```text
人名
企业名
机构名
金额
时间
地点
产品名
```

在金融、法律、医疗等垂直领域，实体往往是检索匹配的重要信号。

### 8.3 语义角色标注

语义角色标注用于提取“谁对谁做了什么”。

它关注的是句子的谓词论元结构，可以帮助系统理解事件关系，而不仅仅是提取关键词。

例如：

```text
谁：征信中心
做了什么：发布声明
对象：个人征信相关事项
```

### 8.4 关键词抽取

也可以使用关键词抽取工具，例如 HanLP、KeyBERT 等。

不过需要注意，不同工具对中文和垂直领域的支持效果不同。通用关键词抽取工具在专业领域中可能准确率不够高。

### 8.5 垂直领域关键词生成模型

对于法律、金融、医疗等专业场景，可以训练专门的关键词生成模型。

文档中提到类似 ChatLaw 的做法，即训练一个 KeyLLM，用于生成更符合领域语义的关键信息。

这种方式成本更高，但在垂直领域效果通常更稳定。

## 9. 是否会产生冗余？

会。

因为系统可能同时索引句子、段落、语义段，召回时可能出现互相包含的内容。

例如：

```text
句子 A 被召回
段落 A 也被召回
语义段 A 也被召回
```

这会造成一定冗余。

但文档中的观点是：在实际测试中，这种方案对细粒度知识和粗粒度跨段落知识的回答效果都比粗暴切分更好。

工程上可以继续通过以下手段优化：

1. 对召回结果去重。
2. 对召回结果重排。
3. 对上下文做压缩。
4. 根据 query 类型动态选择句子级、段落级或语义段级召回。

但优先级上，应该先保证召回完整，再考虑去冗余。

## 10. 面试标准回答

可以这样回答：

```text
要让 LLM 回答全面的粗粒度跨段落知识，关键不是只优化 Prompt，而是要优化 RAG 的检索和切片策略。

首先，文档不能简单按照固定长度、PDF 换行符或 HTML 标签切分，而应该做语义切分，把表达同一主题、存在主从关系或补充关系的段落合并成完整语义块。

其次，可以构建“关键信息 -> 原始文本”的二级索引。检索时只对关键信息做 embedding，提高向量匹配的准确性；召回命中后，再映射回对应的原始文本，把完整上下文交给 LLM。

然后，可以通过篇章分析、BERT 相邻句判断、NER、关键词抽取、语义角色标注等方式提升语义切分和关键信息抽取质量。

这样既能避免 chunk 太小导致跨段落信息召回不全，也能避免 chunk 太大带来大量噪声。最终让 LLM 基于完整、准确、低噪声的上下文进行总结回答。
```

## 11. 追问 1：为什么说重点在检索，而不是 LLM？

因为在 RAG 系统中，LLM 的回答边界通常由 context 决定。

如果 context 中只有两点声明，LLM 很难稳定回答三点声明。即使它回答了三点，也可能是猜测或幻觉。

所以对于知识库问答，优先要解决的是：

```text
相关内容有没有被召回？
召回内容是否完整？
召回内容是否噪声过多？
```

Prompt 可以约束表达方式，但不能弥补缺失的事实依据。

## 12. 追问 2：如何判断应该用细粒度召回还是粗粒度召回？

可以根据 query 类型动态判断。

如果用户问的是事实型问题，例如金额、时间、姓名、定义，可以优先使用句子级或短段落级召回。

如果用户问的是总结型问题，例如“有几点”“有哪些原因”“流程是什么”“整体方案是什么”，则应该优先召回语义段、章节或多段上下文。

也可以同时召回多个粒度，然后进行去重和重排。

```text
事实型问题：句子级召回更合适。
总结型问题：语义段或章节级召回更合适。
复杂问题：多粒度召回 + 重排更合适。
```

## 13. 追问 3：这个方案有哪些工程风险？

第一，语义切分成本较高。

篇章分析、BERT 语义判断、关键词抽取都会增加文档预处理成本。

第二，关键信息抽取质量会影响召回效果。

如果关键信息抽错了，即使原文是完整的，也可能无法被正确召回。

第三，垂直领域效果依赖领域适配。

通用模型在法律、金融、医疗等场景中可能不够准确，必要时需要微调 embedding 模型或训练专门的关键词生成模型。

第四，多粒度召回会带来冗余。

需要通过去重、重排、上下文压缩等方式控制最终传给 LLM 的内容长度。

## 14. 记忆口诀

可以用下面这句话记住这道题：

```text
跨段落问答，先别急着调 Prompt；先语义切分，再关键信息索引，召回原文后交给 LLM 总结。
```

更短的版本：

```text
语义切分保完整，关键信息提召回，原文映射给模型。
```
