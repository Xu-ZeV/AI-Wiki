### 能力展示可以怎么讲？

我想用 MetaLIMS 项目来展示我的业务理解和 Java 后端开发能力。这个系统的核心价值是把实验室检测业务线上化，并围绕最终报告交付实现数据结构化、流程可追溯和报告自动化。

从业务角度看，客户最终拿到的是检测报告，但报告不是独立产生的。它背后需要合同、案件、样品、测试计划、测试项目、设备、实验数据和报告模板共同支撑。系统要解决的问题就是把这些数据和流程串起来，减少人工整理报告的成本，同时保证每一步都有记录，后续可以追溯。

样品流程通常是从合同开始。合同确认后，样品管理员根据合同做样品入库；入库后通知交付专员；交付专员再根据合同和案件把样品分发给不同实验室。实验室主管或管理员根据案件进行领样和分样，把样品分配给对应测试计划和测试工程师。测试过程中产生结构化实验数据，如果多个实验室或多个测试项目需要共用样品，还会涉及转样。测试结束后样品还库，实验数据进入报告自动化流程，最终生成客户报告。

从数据关系上看，我理解主链路是合同、案件、测试计划、测试项目、样品、设备和报告。合同是上层业务入口，一个合同下可以有多个案件；一个案件下可以有多个测试计划；测试计划下面是具体测试项目；样品会跟随合同或案件流转，并在测试计划执行时关联到具体测试项目；设备是测试项目执行时使用的资源；最后测试数据按照报告模板汇总成报告。

后端设计上，我认为这个系统有几个关键点。第一是状态流转要严格，比如样品从入库到领样、分样、测试、转样、还库，每一步都要校验当前状态是否允许操作，不能只依赖前端按钮控制。第二是事务一致性，比如一次操作可能同时影响样品、案件、测试计划和操作日志，需要用 `@Transactional` 保证要么一起成功，要么一起回滚。第三是可追溯，关键操作需要记录操作人、操作时间、业务对象、操作类型、修改前后值和结果状态。第四是权限控制，菜单权限决定用户能看到什么，接口权限保证后端不会被绕过。

我参与的模块里，设备维修闭环比较能体现状态流转设计。设备会经历保养、停用、维修、启用等状态，后端需要限制非法跳转，并记录每次操作的维修记录和状态变化。汽车电子 EMC 工程模块则涉及多张辅助从表和案件状态逻辑，比如样品功能表、样品端口表、附件资料表、项目人员关联表，以及取消、确认、终止、退回等操作。这里的重点是结合当前状态和关联数据完整性判断操作是否允许。

另外，我也参与了全局异常捕获、权限菜单调整和全局查询框重构。全局异常主要通过统一异常处理，把业务异常和系统异常转换成前端可识别的错误码和错误信息。查询框重构则是按不同菜单设计查询类，把前端传入的条件映射为后端查询对象，再由后端按业务规则构建查询条件，避免直接拼接字段导致 SQL 注入或逻辑散乱。

项目里还有一个 AI 标准查新功能，整体思路是通过 LiteLLM 网关调用模型，用 LangChain 集成 Tavily 搜索工具，把搜索结果作为上下文给模型分析，再结构化返回给前端。这个功能让我接触到 AI 工具链在业务系统里的落地方式，也让我意识到 AI 功能不能只靠模型直接回答，还要关注检索来源、结构化输出和业务可用性。

通过这个项目，我最大的提升是从“能把接口写通”转向“能理解业务链路并考虑系统一致性”。我认为我的优势是学习和适应比较快，愿意先把业务流程跑通，再做开发；同时对状态流转、数据关系、异常处理、权限和查询这些后端基础能力有真实项目经验，能够在业务系统里比较快地进入工作状态。

## 3. 面试官提问（5 到 10 分钟）

### MetaLIMS 主要解决什么问题？

推荐回答：

它主要解决检测实验室的流程线上化、报告自动化和数据可追溯问题。客户最终要的是检测报告，但报告背后依赖合同、案件、样品、测试计划、设备和实验数据。MetaLIMS 把这些业务对象统一管理，让样品流转、测试执行、数据沉淀和报告生成都有系统记录，减少人工整理成本，也方便后续追溯和统计。

### 样品从入库到报告生成的流程是什么？

推荐回答：

样品一般跟着合同来。合同确认后样品管理员入库，之后通知交付专员；交付专员根据合同和案件分发到不同实验室；实验室主管或管理员领样、分样，再分配给测试计划和测试工程师；测试过程中产生实验数据，必要时会转样；测试完成后样品还库；最后系统根据测试数据和报告模板自动生成检测报告。

### 核心表关系怎么理解？

推荐回答：

核心链路可以理解为合同、案件、测试计划、测试项目、样品、设备和报告。合同 1:N 案件，案件 1:N 测试计划，测试计划 1:N 测试项目。样品会和合同、案件、测试计划或测试项目产生关联，设备会和测试项目产生使用记录，测试数据最后进入报告自动化流程。

### 设备维修模块怎么设计？

推荐回答：

设备维修模块围绕设备状态做闭环管理，流程包括保养、停用、维修、启用。设计上可以把设备主表和维修记录表分开：设备主表保存当前状态和基础信息，维修记录表保存每次维修或保养的操作记录。后端要限制非法状态跳转，比如未停用不能直接维修，维修未完成不能启用，同时关键状态变化要写操作日志。

### 汽车电子 EMC 工程模块你做了什么？

推荐回答：

我参与了汽车电子 EMC 工程模块的辅助从表和状态逻辑，包括样品功能表、样品端口表、开案或结案附件资料表、项目人员关联表等。除了基础增删改查，还涉及案件取消、确认、终止、退回等状态变化。这里重点是根据当前状态、关联数据是否完整、是否已有测试计划或测试数据，判断操作是否允许执行。

### 系统可追溯怎么实现？

推荐回答：

关键是记录操作日志和状态变化。日志字段一般包括操作人、操作时间、业务模块、业务对象类型、业务对象 ID、操作类型、修改前数据、修改后数据、请求 IP、接口路径和结果状态。通用日志可以用 AOP 或注解统一处理，但样品状态、案件状态、报告数据这类关键业务操作，我更倾向于在业务代码里明确记录修改前后值，并让日志参与事务。

### 一次操作同时修改多张表，如何保证一致性？

推荐回答：

会把相关业务修改和关键操作日志放在同一个事务里，通过 Spring 的 `@Transactional` 控制事务边界。比如一次领样操作同时修改样品状态、案件进度、测试计划和日志，如果中间任何一步失败，就抛出异常回滚，避免出现业务数据成功但日志失败，或者日志写了但业务数据没成功的问题。

### 全局异常捕获怎么做？

推荐回答：

通常用 `@RestControllerAdvice` 配合 `@ExceptionHandler` 做统一异常处理。业务异常返回明确错误码和提示，比如参数不合法、状态不允许流转、数据不存在；系统异常统一兜底，记录日志后返回通用错误，避免把数据库异常、空指针或第三方异常直接暴露给前端。

### 权限菜单调整怎么理解？

推荐回答：

菜单权限本质是用户、角色、菜单和接口权限之间的关系。用户通过角色获得菜单权限，菜单决定前端展示哪些页面和按钮，但后端接口仍然要做权限校验，不能只依赖前端隐藏按钮。公共菜单适合多个角色共用，独立菜单适合特定岗位或模块专属能力。

### 全局查询框重构怎么做？

推荐回答：

目标是让不同菜单列表支持统一入口的关键字查询，但每个菜单对应的字段和规则不同，所以不能固定写一套 SQL。可以按菜单或业务模块设计查询类，把前端条件映射成后端查询对象，再用 MyBatis-Plus 的 `LambdaQueryWrapper` 或 XML SQL 构建查询。重点是避免前端直接传字段拼 SQL，降低注入风险，也让查询逻辑更好维护。

### 在项目中是否遇到过系统性能瓶颈？你是如何分析和优化的？

推荐回答：

遇到过。比较典型的是 MetaLIMS 里报价单列表查询变慢的问题。这个列表不是单表查询，一份报价单会关联多份现场试验记录，现场试验记录下面又有关联的试验项目，试验项目还会关联多份试验数据。前期数据量不大时问题不明显，但客户环境中报价单累计到 3 万条左右后，列表查询开始明显变慢。

我当时不是一上来就加缓存，而是先从查询链路定位问题，主要分三层处理。

第一层是服务层优化。原来的实现里，有一部分展示字段是在 Service 层遍历报价单列表，然后在循环里逐条查询或逐条 set 关联数据，这会导致典型的 N+1 查询问题。优化时，我把这些按单条查询的逻辑改成批量查询：先收集报价单 ID 或关联 ID，一次性查出关联数据，再用 `Map<id, data>` 做内存映射，最后回填到列表对象里。这样减少了数据库往返次数，也让代码逻辑更清晰。

第二层是数据模型优化。报价单列表里需要展示多个试验项目、多个样品等汇总字段，原来每次打开列表都要通过多表关联查询后再拼接字符串。这个逻辑对列表查询压力比较大，所以我把这类列表高频展示、但实时计算成本较高的字段拆到一张报价单扩展表里。业务数据更新时同步维护扩展表，列表查询时直接读取汇总后的展示字段。相当于把查询时的计算压力，平摊到每次数据变更时处理，适合这种“读多写少、列表展示频繁”的场景。

第三层是数据库执行计划优化。我用 `EXPLAIN` 看 SQL 执行计划，重点看 `type`、`key`、`rows` 和 `Extra`，发现有些关联没有正确命中索引。排查后主要有两个原因：一个是客户数据库和测试环境的表名大小写策略不一致，导致线上 SQL 兼容性和排查成本变高，后面统一了表名小写规范；另一个是部分关联字段的字符集或排序规则不一致，左连接时发生隐式转换，导致索引效果变差。后面把关联字段的类型、长度、字符集和排序规则统一到同一套项目规范，比如统一使用项目约定的 `utf8mb4` 系列字符集和排序规则，避免因为隐式转换影响索引。

这次优化后，我最大的体会是，性能问题要先定位瓶颈再选方案。如果问题根因是 N+1 查询、多表实时聚合和索引失效，直接加 Redis 缓存不一定是最优解，因为缓存还会带来一致性和失效策略问题。更稳妥的做法是先减少 SQL 次数、降低列表查询复杂度、保证索引有效，再根据读写频率决定是否需要缓存。

**回答要点**

- 先说明具体业务场景：报价单列表，多层关联，数据量到 3 万条左右后变慢。
- 说明分析方式：查看服务层调用链，排查循环查询；用 `EXPLAIN` 看执行计划和索引命中情况。
- 服务层优化：把循环逐条查询改成批量查询，再用 ID 映射回填。
- 数据模型优化：把列表高频展示的聚合字段放到扩展表，写入或更新时同步维护。
- 数据库优化：统一表名规范，统一关联字段类型、长度、字符集和排序规则，避免隐式转换导致索引效果变差。
- 表达缓存取舍：不是所有慢查询都应该直接上缓存，先优化 SQL 和数据模型，再看是否需要 Redis。

**表达提醒**

- 不要只说“加索引解决了”，要讲清楚如何发现索引没有生效，以及为什么没有生效。
- 如果记不清具体字符集或排序规则，不要硬编，可以说“统一为项目约定的同一套字符集和排序规则”。
- 可以强调这是一次综合优化：应用层减少查询次数，数据模型降低实时聚合成本，数据库层保证索引可用。

### AI 标准查新功能怎么做？

推荐回答：

整体流程是后端接收用户查询需求，通过 LiteLLM 调用大模型，同时用 LangChain 集成 Tavily 搜索工具获取外部检索结果，再把检索内容作为上下文交给模型分析，最后结构化返回。关键点是不能只让模型凭空回答，而是要结合搜索结果提升可依据性，返回结构里可以包含标准名称、相关性说明、来源摘要和建议结论。

### 你最大的项目收获是什么？

推荐回答：

最大的收获是对复杂业务系统的开发方式有了更完整的认识。MetaLIMS 里很多功能不是简单 CRUD，而是要考虑状态流转、权限边界、数据追溯、事务一致性和报告准确性。它让我意识到后端开发要先理解业务链路，再设计数据模型和接口逻辑。

## 4. 面试官答疑（1 到 5 分钟）

### 当面试官问“你有什么想了解的吗”时怎么回答？

可以问 3 个问题，不要一次问太多：

- 这个岗位入职后主要负责新业务开发，还是已有系统的迭代维护？
- 团队现在 Java 后端主要使用哪些技术栈？比如 Spring Boot、MyBatis、Redis、消息队列这些在项目里的使用深度是怎样的？
- 如果我入职，前三个月对这个岗位的核心期待是什么？更看重业务熟悉速度、代码交付，还是问题排查能力？
- 当前团队对代码质量和上线流程有什么要求？比如代码评审、测试环境、接口文档、日志规范等。
- 这个岗位后续有没有机会参与模块设计、性能优化或中间件相关工作？

### 反问时如何收尾？

我的问题主要是想判断岗位职责和我当前经验的匹配度。从刚才沟通看，我对业务系统后端开发、状态流转、数据一致性和问题排查比较感兴趣，也希望入职后能尽快熟悉业务，先把模块开发和维护工作做好，再逐步承担更复杂的设计和优化任务。

### 哪些问题不建议优先问？

- 不要一开始就连续追问薪资、加班、调休、年终奖。
- 不要问官网或招聘 JD 已经写清楚的基础信息。
- 不要问“你觉得我表现怎么样”，可以改成“如果后续还有流程，我需要重点补充哪些材料或准备哪些方向？”

## 5. 临场表达提醒

### 临场表达时需要注意什么？

- 讲项目时先讲业务价值，再讲技术实现。
- 少说“然后”，多用“第一、第二、最后”。
- 不确定的技术细节用“我参与的部分是”限定边界。
- 不要把项目技术栈里的所有中间件都说成自己深度负责。
- 讲状态流转时一定要提非法状态校验。
- 讲日志追溯时一定要提修改前后值和事务一致性。
- 讲 Java 后端理解时，不要只说 CRUD，要讲数据模型、接口设计、事务、权限、异常、性能和可维护性。

## 6. 可背诵核心句

### 可以背诵哪些核心句？

MetaLIMS 的核心不是简单的实验室台账，而是围绕检测报告交付，把合同、案件、样品、测试计划、设备、实验数据和报告模板串成一条可追溯的业务链路。

我在项目中的主要价值，一方面是参与设备维修闭环、汽车电子 EMC 工程模块等业务开发；另一方面是参与全局异常、权限菜单、查询框重构、AI 标准查新等工程能力建设。

我理解 Java 后端岗位不只是写接口，更重要的是把业务规则稳定准确地落到系统里，保证数据一致、流程可控、问题可查、系统可维护。
