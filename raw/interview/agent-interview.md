 ## 一.架构层

### 1.为什么没有直接上 LangGraph 或完整 ReAct 循环？

- 考察点：阶段性架构能力。
- 答题要点：当前工具边界清晰、第一阶段不需要多轮反思和循环执行；受控单轮工具计划成本更低、可测性更好。

### 2.`chat_stream()` 为什么要拆成 Planner、Executor、Final Reply 三段？

- 考察点：职责分离。
- 答题要点：Planner 决策工具，Executor 执行受控能力，最终回复模型负责表达；防止模型边生成边乱调工具。

### 3.为什么返回后端的数据结构是{event, data} 

- 考察点：接口设计

- 前端可以根据 `event` 做统一分发，不需要猜 `data` 里面是什么。
- `data` 只关注业务内容，`event` 负责描述语义，职责更清晰。
- 后续扩展方便，比如新增 `progress`、`thinking`、`done`、`error` 事件，不容易破坏已有结构。
- 对 AI 流式返回很友好，前端可以边收到 `message` 边渲染，收到 `done` 后结束加载状态。

### 4.SSE 和 WebSocket的区别，当前场景为什么选sse,SSE 相比 WebSocket 在当前场景有什么优势？

| 对比项     | SSE                                     | WebSocket                             |
| ---------- | --------------------------------------- | ------------------------------------- |
| 通信方向   | 服务端到客户端单向推送                  | 客户端和服务端双向通信                |
| 协议基础   | 基于 HTTP，`text/event-stream`          | 先 HTTP 握手，再升级为 WebSocket 协议 |
| 浏览器 API | `EventSource` 或 `fetch stream`         | `WebSocket`                           |
| 数据格式   | 天然支持 `event`、`data`、`id`、`retry` | 需要自己定义消息协议                  |
| 重连机制   | 浏览器原生支持自动重连                  | 需要前端自己实现心跳、重连            |
| 适合场景   | AI 流式输出、通知、日志、进度推送       | 聊天室、协同编辑、游戏、实时双向控制  |

回答：当前场景是 AI 面试回答或分析结果的流式返回，本质上是客户端发起请求后，服务端持续推送生成中的内容。这个通信方向主要是服务端到客户端，所以 SSE 已经足够。相比 WebSocket，SSE 基于 HTTP，实现和部署成本更低，前端可以直接按 `event` 监听不同消息类型，比如 `message`、`done`、`error`，而且它天然支持自动重连和事件格式。WebSocket 更适合强双向、高频互动的场景，比如聊天室、协同编辑或游戏，但在当前 AI 流式输出场景下会增加心跳、重连、协议封装等额外复杂度。
